# 서비스 상세 섹션

현재 운영 중인 서비스가 무엇인지, 어떻게 동작하는지 서술한다. 투자위원회가
"이 회사가 무엇을 만들어 어떤 고객에게 제공하는가"를 이해할 수 있어야 한다.
기능 나열이 아니라 실제 동작 흐름·구조를 담는다.

## 정보 소스 (우선순위)

| 순위 | 소스 | 무엇을 |
|------|------|--------|
| 1 | Investment Theme | 서비스의 본질과 구조 |
| 2 | **노션 미팅록** | 대표가 설명한 실제 동작, 개발 현황 (`22_노션연동.md`) |
| 3 | IR 덱 | 제품 슬라이드·스크린샷·아키텍처 (`21_IR덱읽기.md`) |
| 4 | 기술 자료 | 기술 스택, 아키텍처 상세 |

---

<CRITICAL>
**#1 — 기능 나열이 아니라 동작으로 쓴다**: "A 기능, B 기능, C 기능이 있음"은
카탈로그다. 사용자가 무엇을 하면 제품이 무엇을 하는지 흐름으로 쓴다.

나쁜 예: `실시간 라이브, 다중 플랫폼 송출, 팬 관리 기능 제공`
좋은 예: `캐릭터를 어드민에 올리면 24시간 라이브가 자동 송출되고, 유튜브·틱톡·치지직에 동시 방송되며 팬 반응 데이터가 수집됨`

**#2 — 이미 만든 것과 만들 것을 구분한다**: 현재 운영 중인 것이 서비스 상세다.
로드맵은 향후 전략 섹션이다. "개발 중", "예정"을 섞지 않는다.

**#3 — 구조와 차별점을 함께**: 단순 소개가 아니라 이 구조가 왜 다른지를 담는다.
(예: 로컬 서버 운영으로 API 비용 없음, HW+SW 번들로 이탈 어려움)

**#4 — 논거를 충분히 전개**: 서비스 구성요소마다 별도 불릿으로 편다. 얕은
소개로 끝내지 말되, 불릿은 짧게(중앙값 68자). save_section이 검사한다.
</CRITICAL>

## 이미지

IR 덱에 제품 스크린샷·아키텍처 다이어그램이 있으면 `21_IR덱읽기.md`에 따라
이미지로 읽고, 핵심을 본문에 서술한다. 필요하면 section_images로 삽입한다.

## 자기 점검

| # | 검사 | 심각도 |
|---|------|--------|
| 1 | 기능 나열에 그쳤는가 (동작 흐름 없이) | ❌ 흐름으로 |
| 2 | 개발 예정 기능을 현재처럼 적었는가 | ❌ 향후전략으로 |
| 3 | 왜 다른 구조인지가 빠졌는가 | ⚠️ 차별점 추가 |
