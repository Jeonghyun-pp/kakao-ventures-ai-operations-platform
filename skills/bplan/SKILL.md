# 비플랜 접수 동기화

접수 1건 = 노션 행 1개. 시트 위치·사람의 편집·재실행과 무관하게 **같은 접수는 두 번 들어가지 않고,
다른 접수는 빠지지 않아야 한다.** 그게 이 스킬의 품질 기준이고, 옛 시스템이 두 번 다 실패한 지점이다.

<HARD-GATE>
스케줄을 켜기 전까지 `sync` 는 사람이 `--dry-run` 보고를 읽고 실행한다. 예외 없음.
— 첫 실행이 만드는 56건은 심사역이 하나씩 볼 대상이다. 잘못 들어간 행은 지우면 되지만,
  잘못 **빠진** 접수는 아무도 모른다. 보고에서 "걸러진 이유" 를 사람이 한 번 봐야 한다.
</HARD-GATE>

## 🔴 하는 일과 안 하는 일

```
한다     노션 행 생성 (새 접수만)  ·  접수 알림 메일에 라벨 부여 + 인박스 제거
안 한다  판정(점수) · To do 이동 · 드랍 초안 · 발송 · 시트 쓰기 · 접수 메일 본문 읽기
```

라벨 이동은 삭제가 아니라 아카이빙이라 되돌릴 수 있다. 판정은 별도 스킬(Phase 2)이 노션 행을
읽어서 하고, 드랍 초안도 별도다. 이 스킬은 그 둘의 **입력**을 만든다.

## 명령

```bash
cd ~/kv
./.venv/bin/python -m skills.bplan.run sync --dry-run          # 계획만. 노션·지메일 쓰기 0
./.venv/bin/python -m skills.bplan.run sync [--limit N] [--since ISO]
./.venv/bin/python -m skills.bplan.run status
./.venv/bin/python -m skills.bplan.run selftest                # 망 불호출 자기검사
```

`--since` 는 바닥선을 사람이 명시할 때만 쓴다(놓친 기간을 아는 사람이 정한다).

## Non-Negotiable Rules

<CRITICAL>
**#1 — 바닥선 이후만 본다**: `max(장부 마지막 착지 시각, 노션 접수키 최대 시각)` 보다 뒤의 접수만
신규 후보다. "노션에 없으면 신규" 로 돌리면 6년치 5,000건을 붓는다(2026-08-13 dry-run 실측 5,033건).
바닥선 근거가 없으면 오늘 자정으로 떨어지고, 과거는 `--since` 로 사람이 넣는다.

**#2 — 멱등 키는 접수키다**: `이메일|접수시각`. 시트 행 서수를 키로 쓰면 행이 하나 밀릴 때
같은 서수가 다른 회사를 가리킨다 — 옛 시스템에서 같은 사람이 드랍 메일을 6통 받았다.
키는 노션 행에 `접수키` 칸으로 심는다. 그래야 "이 접수가 이미 있나"를 노션에 물을 수 있다.

**#3 — 키 없는 옛 행은 이메일 + 생성시각으로 대조한다**: 2026-08-30 에 옛 코드로 들어간 68행은
접수키가 없다. 키만 보면 다시 만든다. 같은 이메일의 키 없는 행이 있고 **그 행이 접수보다 뒤에
생겼으면** 같은 접수다. 행이 접수보다 먼저 생길 수는 없으니 행 생성 뒤의 재접수는 새것이다.
기업명은 대조에 쓰지 않는다 — 심사역이 노션 제목을 고쳐 쓴다.
  나쁜 예: (이메일, 기업명) 대조 → "주식회사 카즈아" vs "주식회사 카즈아 (MAKEMORY)" 가 어긋나 옛 접수 10건을 다시 만든다 (첫 dry-run 실측)
  좋은 예: 이메일 대조 + "행 생성시각 ≥ 접수시각" → 같은 사람의 9/1 재접수(사랑의빛)는 새 행, 8/28 접수(포튜나헬릭스)는 옛 행

**#4 — 노션에 행이 없는 접수 메일은 건드리지 않는다**: 라벨만 붙여 인박스에서 빼면 아무도 추적하지
않는 접수가 조용히 사라진다. 그런 메일은 `🔴 라벨 보류` 로 보고하고 종료코드 2 로 끝낸다.
대신 그 메일은 인박스에 남아 `mail` 스킬이 `protect` 로 지킨다.

**#5 — 답장(`Re:`)은 잡지 않는다**: 접수 알림 제목과 같은 문구라도 창업자의 후속 메일은 사람이
봐야 한다. 제목이 `[카카오벤처스]… 로부터 접수된 사업계획서` 로 **정확히** 끝날 때만 접수 알림이다.

**#6 — 담당자·To do 는 라이브 옵션으로 대조한다**: 노션은 모르는 select 값을 주면 **새 옵션을 조용히
만든다** — 오타 하나로 없는 사람이 생기고 그날 접수분 전부가 거기 배정된다. 통로가 만들기 전에 막는다.
사람을 늘리려면 노션에서 먼저 옵션을 만든다. 코드가 명부를 만들지 않는다.

**#7 — 시트 헤더는 접두사로, 하나라도 없으면 멈춘다**: 질문 문장 전체를 키로 쓰면 폼 문구 한 글자에
그 칸이 조용히 빈 값이 된다. 빈 칸이 들어가면 판정이 빈 칸을 근거로 Red 를 낸다.
</CRITICAL>

바닥선 근거가 없을 때 — 순서대로:
  1순위: `--since` 를 사람이 명시한다
  최후: 오늘 자정 (되살리기보다 안전한 쪽)
  금지: "노션에 없으면 전부 신규"

## 실행 순서

```
① 인증    시트 · 지메일 · 노션 셋 다 먼저 본다. 나중에 401 로 알면 0건과 구별이 안 된다
② 읽기    시트 전량(5,600행) · 노션 전량(칸 4개만: 접수키·기업명·이메일·생성시각)
          · 인박스의 접수 알림(라벨 없는 것) 한 번 — 계획에 "접수 메일 유무" 를 싣는다
③ 고르기  바닥선 이후 → 접수키 없음 → 옛 행 중복 아님 → 신규. 걸러진 이유를 센다
④ 생성    노션 행. 통로가 되읽어 확인한 것만 장부에 `landed`
⑤ 라벨    ②의 접수 알림 중 노션에 기업명이 있는 것 — 라벨 + 인박스 제거
          대상을 지메일 상태로 정하므로 지난 실행의 실패분·옛 행의 메일이 같은 코드로 잡힌다
⑥ 보고    ~/kv-data/bplan/reports/<ts>.md · 숫자는 장부에서
```

## Quick Reference

| 항목 | 값 | 어디서 |
|---|---|---|
| 담당자 | `에반 Evan` | `run.py` ASSIGNEE · 노션 옵션이어야 한다 |
| 라벨 | `3. Evan` | `run.py` GMAIL_LABEL · 드랍이 이 안에서 원본을 찾는다 |
| 신규 행 `to do` (소문자) | `Newly Added` | 노션 옵션. "To do" 로 쓰면 통로가 막는다 |
| 시트 | `.env` SPREADSHEET_URL · WORKSHEET_NAME | 표시 문자열로 읽는다(접수키 형식 유지) |
| 노션 DB | `.env` NOTION_DATABASE_ID = Bplan 3.0 DB | `register_writable("bplan")` |
| 장부 | `~/kv-data/_ledger/bplan.jsonl` | `landed` key=접수키 · `labeled` key=메일번호 |
| 종료코드 | 0 정상 · 1 인증/입력 · 2 온전하지 않음 · 3 이중 실행 | |

## 검사

```bash
./.venv/bin/python -m skills.bplan.run selftest   # 헤더·타임스탬프·키·정규화·중복 규칙 (망 0)
./.venv/bin/python check_intent.py                 # A1 시트 통로 등록 · A8 발송 0건 · A6 숫자 없음
```

`selftest` 가 하나라도 ❌ 면 `sync` 를 돌리지 않는다. ⑤ 정규화가 실제로 첫 판에서 실패했다 —
`(주)차엔차` 가 `주차엔차` 로 남았다. 검사가 없었으면 옛 행 대조가 조용히 어긋났을 것이다.

## 스케줄 — 아직 선언하지 않는다

선언만 하고 안 켜면 A9 가 실패한다(선언은 있는데 발동 안 하는 가드). 첫 실행을 사람이 보고
매일 돌리기로 정하면 이 프런트매터에 한 줄을 넣고 `schedule.py install --apply` 한다:

```yaml
schedule:
  - { cmd: sync, when: "매일 09:20", why: "메일 관찰(10:00) 앞. 접수 메일을 먼저 라벨로 옮겨 두면 관찰이 그걸 접수 알림으로 본다" }
```

## 알아둘 것

**옛 시스템의 비플랜 코드(mail-harness `jobs/bplan_*.py`)는 2026-09-25 에 지웠다 — kv-automation 리포의 커밋 `18bdaad` 직전(HEAD~1)에 있다.**
sync 는 이 스킬이 대체했다. drop 과 score 는 아직 대체물이 없다 — score 는 판정 기준을 새로 쓰기로 해서
2026-09-02 에 배선을 끊었고, Phase 2 판단 에이전트가 그 자리를 새로 채운다.

**같은 사람이 여러 번 접수하면 행도 여러 개다.** 접수 1건 = 행 1개가 원칙이다. "같은 사람에게
드랍 메일 한 통"은 드랍 쪽의 멱등(이메일 + 1주일)이 지킨다 — 여기서 합치지 않는다.

**첫 실행(2026-09-16)이 잡은 것 둘.** ① 노션 칸 이름은 `to do` 소문자다 — 통로가 쓰기 전에 막아 한 행도 안 생겼다.
② 노션은 제로폭 문자(U+200B)도 조용히 지운다 — Example Company E 행이 되읽기 불일치로 실패했고, 통로의 `sanitize` 가
그 부류를 지우도록 넓혔다. 행은 생겼으므로 장부에 손으로 한 줄 넣고 라벨은 재실행이 붙였다.

**시트를 표시 문자열로 읽는 이유**: 노션의 옛 접수키가 한국어 로케일 타임스탬프 문자열에서 만들어졌다.
숫자(일련번호)로 바꾸면 키가 어긋나 같은 접수가 두 번 들어간다.
