## 0. 명제

> **AI가 구현 비용을 거의 없애면, 핵심 역량은 코드를 작성하는 능력에서
> 시스템을 운영 가능한 구조로 만드는 능력으로 이동한다.**

이 문서가 존재하는 이유는 그 "운영 가능한 구조"가 무엇으로 구성되는지를 **순서까지 포함해** 고정하기 위해서다.

### 관통하는 두 명제

전체 구조에서 반복되는 실패의 뿌리는 둘뿐이다. 모든 단계는 이 둘 중 하나의 구현체다.

```
① 보고된 성공과 실제 반영은 다른 사건이다      → 2 · 5 · 8단계
② 실패는 예외가 아니라 정상 상태다             → 4 · 9 · 10단계
```

```
exit 0    → 프로세스가 끝났다      (산출물이 있다는 뜻이 아니다)
HTTP 200  → 요청이 수락됐다        (반영됐다는 뜻이 아니다)
push 201  → 발송이 접수됐다        (표시됐다는 뜻이 아니다)
send 성공  → 명령을 보냈다          (처리됐다는 뜻이 아니다)
```

## 1. 평면 분해

시스템은 5개 평면으로 나뉜다. 이 분해는 단계 순서와 무관하게 항상 유효하다.

| 평면 | 책임 | 구현 단계 |
|---|---|---|
| **Execution Plane** | 실제 작업 수행 | 3 · 6 |
| **Control Plane** | 승인 · 쿼터 · 권한 · 스케줄링 | 2 · 8 |
| **State Plane** | 잡 상태 · 로그 · 체크포인트 | 3 · 4 |
| **Observation Plane** | 대시보드 · 알림 · 인시던트 | 7 · 9 |
| **Recovery Plane** | 재시작 · 재개 · 정리 · 에스컬레이션 | 4 · 8 · 9 |

애플리케이션은 이 평면들 **위에** 얹힌다. 애플리케이션이 평면의 기능을 자체 구현하기 시작하면 그것이 구조 붕괴의 첫 신호다.

## 3. 전제 사슬 — 왜 이 순서인가

각 단계는 다음 단계의 **전제**다. 순서를 바꾸면 뒤 단계가 성립하지 않거나 N배 비싸진다.

```
1 공통 런타임          없으면 이후 모든 계층이 N벌로 복제된다
      ↓
2 어드미션 컨트롤       무인화는 "사람이 실행 버튼을 누른다"는 암묵적 예산 가드를 제거한다
      ↓
3 상태 프로토콜         상태가 외부화돼야 재개 · 관측 · 복구가 성립한다
      ↓
4 지속 실행            중단이 기본 조건인 환경에서는 재개가 전제다
      ↓
5 산출물 검증          "이어서 끝냈다"와 "제대로 나왔다"는 다른 사건이다
      ↓
6 프로세스 감독         성공 판정 없이 무인화하면 조용히 틀린 걸 매일 생산한다
      ↓
7 관측 평면            무인 실행은 아무도 보고 있지 않다
      ↓
8 정책 집행 · 안전장치   막힌 게 보여야 원격에서 풀 수 있다
      ↓
9 장애 감지 · 주입       안전장치 없는 카오스 실험은 그냥 사고다
      ↓
10 점진적 롤아웃        실패 목록이 있어야 자동화 승격을 숫자로 말할 수 있다
      ↓
11 페이브드 로드 검증    기반의 가치는 다음 산출물의 리드타임으로만 관측된다
      ↓
12 운영 이양           만든 사람 없이 도는지가 최종 판정
```

**읽는 법** — 이 순서는 우리 환경의 병목 순서다. 다른 환경에서는 달라진다.
고정해야 할 것은 순서 자체가 아니라 **"무엇이 무엇의 전제인가"를 따지는 습관**이다.

## 4. 각 단계 정의

### 1 · 공통 런타임 — Shared Runtime / Internal Platform

**정의** — 여러 애플리케이션이 각자 복제하는 횡단 관심사를 하나의 계층으로 뽑아, 애플리케이션이 도메인 로직만 갖게 만드는 것.

**구성요소** — 시크릿 저장소 · 외부 시스템 클라이언트 · 알림 채널 · 자원 게이트 · 잡 추상 · 헬스 프리미티브 · 단일 런타임 환경.

**왜 이 자리인가** — 뒤에 오는 모든 단계가 N벌로 복제될지 1벌로 상속될지가 여기서 갈린다.

**이 단계의 비가역 결정 3가지**

| 결정 | 잘못하면 |
|---|---|
| 시크릿 저장 방식 | 머신 종속 저장소를 쓰면 환경 이전 자체가 불가능해진다 |
| 경로 기준 | 절대경로가 하나라도 남으면 다른 머신에서 통째로 깨진다 |
| 공통 / 고유 경계 | 너무 넓으면 결합도, 너무 좁으면 복제. 되돌리기 비싸다 |

**성공 신호** — N번째 애플리케이션의 이식이 첫 번째보다 눈에 띄게 빠르다.

**일반 이름** — internal platform · paved road · 12-factor config · DRY vs 복제 비용

---

### 2 · 어드미션 컨트롤 · 실행 계층 분리 — Admission Control · Execution Tiering

**정의(전자)** — 모든 실행 주체가 공유 자원(쿼터 · 예산 · rate limit)을 소비하기 전에 통과해야 하는 **단일 결정 지점**.

**정의(후자)** — 가용성 요구가 다른 워크로드를 서로 다른 실행 계층에 배치하는 것.

**왜 이 자리인가** — 무인화가 시작되는 순간 사람이라는 암묵적 예산 가드가 사라진다. 그 가드를 코드로 대체하기 전에 무인화하면 안 된다.

**핵심 실패 모드 — retry storm**

```
A가 429 → 재시도
B가 429 → 재시도        각자는 국소적으로 합리적
C가 429 → 재시도
→ 남은 자원을 3배 빠르게 소모하고 셋 다 계속 실패
   재시도 자체가 요청이라 rate limit 창이 더 길어진다
```

해결은 각 주체를 똑똑하게 만드는 것이 아니라 **결정 지점을 하나로 올리는 것**이다.

**설계 원칙 — 게이트와 차단선을 분리한다**

```
게이트(preflight)   실행 전 · 중단 비용 0    → 보수적이어도 된다
차단선(budget)      실행 중 · 이미 소비됨     → 추정치에 밀착시키면 안 된다
```

둘을 같은 값으로 두면 추정 오차만으로 전체가 0건이 된다.
월 가드는 추정이 아니라 **실제 청구액** 기준이어야 한다.

**성공 신호** — 실행 환경이 며칠 꺼져 있어도 상시 계층의 데이터 연속성이 끊기지 않고,
어떤 작업을 돌려도 실행 전에 잔여 예산이 먼저 출력된다.

**일반 이름** — admission control · rate limiting · retry storm · backoff · circuit breaker · workload tiering

---

### 3 · 잡 러너와 상태 프로토콜 — Job Runner · State Protocol

**정의** — 작업을 잡 단위로 감싸고, 그 상태를 다른 프로세스가 읽을 수 있는 형식으로 외부화하는 규약.

```
jobs/<id>/
  request.json    무엇을 요청받았나
  state.json      지금 어느 단계인가
  events.jsonl    무엇을 수행했나 (append-only)
  artifacts/      산출물
  stderr.log
```

```
requested → queued → running → validating → completed | failed
```

전이마다 넷을 정의한다 — **누가 바꾸나 · 어디 기록되나 · 중복 전이 가능한가 · 죽으면 남나.**

**왜 이 자리인가** — 이 규약 하나가 4 · 6 · 7 · 9 · 11단계를 전부 가능하게 만든다.

| 규약이 있어서 가능해지는 것 | 단계 |
|---|---|
| 어디까지 됐는지 알고 이어감 | 4 |
| 죽음을 판정할 근거 | 6 |
| 읽기만으로 전체 관측 | 7 |
| 장애 주입 후 결과 확인 | 9 |
| 새 앱이 규약만 따르면 공짜 상속 | 11 |

> 파일을 DB의 싼 대체물로 쓰는 것이 아니라, **프로세스 간 상태 교환 프로토콜**로 쓰는 것이다.

**강제 사항 2개**

- **append-only 로그** — 덮어쓰지 않는다. 중단돼도 앞부분이 남는다
- **원자적 쓰기 (tmp → rename)** — 비원자적 쓰기는 재실행 시 중복 산출물을 만든다

**동시성 정책** — heavy는 동시 1 + 큐, light는 병렬.
잡 하나가 내부적으로 수백 프로세스로 fan-out할 수 있다. 병렬성이 많다고 항상 빠르지 않다.

**성공 신호** — 실행 중인 잡을 `kill -9` 해도 상태 디렉토리만 보고 무엇이 어디까지 됐는지 안다.

**일반 이름** — state machine · append-only log · atomic file write · idempotency · producer-consumer · worker pool

### 4 · 지속 실행 — Durable Execution

**정의** — 중단을 실패가 아니라 **일시정지**로 취급하고, 재개 시 완료된 단계를 건너뛰며 이어가는 실행 모델.

**구성요소** — 단계별 체크포인트 · resume 메타 · 중간 산출물 보존 · 재시도 횟수 · 캐치업 드레인.

**왜 이 자리인가** — 실행 환경의 가용성이 보장되지 않는 시스템에서는 중단이 예외가 아니라 기본 조건이다.
이 전제가 성립하면 스케줄 모델 자체가 바뀐다.

```
버림:  "매일 정해진 시각에 실행"                  ← 절대 시각 기준
채택:  "마지막 실행 이후 N시간 지났으면,           ← 경과 시간 기준
        다음에 가용해질 때 실행"
```

이것을 **최소 간격 모델(minimum interval)** 이라 부른다. 고정 주기가 아니라 하한선이다.

**부수 규칙** — 정의되지 않은 주기 이름은 조용히 강등하지 말고 크게 경고한다.
조용한 강등은 며칠 뒤에야 발견된다.

**성공 신호** — 실행 환경을 사흘 닫아뒀다 열면 밀린 잡이 스스로 드레인되고 중복 실행 0건.

**일반 이름** — checkpointing · durable execution · at-least-once · duplicate delivery · idempotency key · compensation

---

### 5 · 산출물 검증 — Artifact Validation / End-to-End Verification

**정의** — 프로세스 종료 코드가 아니라 **기대 산출물의 존재와 형태**로 성공을 판정하는 계층.

**검사 항목** — 파일 존재 · 필수 섹션 · 최소 크기 · 스키마 적합 · 빈 값 아님 · **쓰기 후 되읽기 확인**.

**왜 이 자리인가** — 4단계에서 재개가 되기 시작하면 즉시 다음 질문이 생긴다.
"이어서 끝냈다는데, 제대로 나온 게 맞나?"

> **프로세스 성공 ≠ 업무 성공.** exit code 0이어도 기대 산출물이 없으면 실패다.

외부 시스템은 **값을 조용히 버리면서 성공 응답을 줄 수 있다.** 그래서 쓰기 후 되읽기가 필요하다.

**컷오버가 여기 붙는 이유** — 구 · 신 시스템이 같은 외부 상태(큐 · 커서 · DB)를 공유하면
병행 실행이 중복과 누락을 만든다. 검증 계층이 있어야 단방향 전환의 성공을 판정할 수 있다.

**성공 신호** — 산출물이 없는 잡이 성공으로 보고되지 않는다.

**일반 이름** — artifact validation · end-to-end verification · side effect verification · cutover strategy

---

### 6 · 프로세스 감독 — Process Supervision

**정의** — 실행 주체를 대화형 세션에서 분리해 독립 프로세스로 만들고,
그 수명 · 재시작 · 스케줄을 OS 수준 감독자에게 위임하는 것.

**세 파일이 각각 다른 질문에 답한다**

```
health file  → 지금 살아 있는가       자주 갱신 · 덮어쓰기
event log    → 무엇을 수행했는가      append-only
state file   → 지금 어느 단계인가     전이 시점에만
```

셋을 하나로 합치면 안 된다 — **갱신 주기와 쓰기 패턴이 다르다.**

**왜 이 자리인가** — 5단계에서 성공 판정이 생겼으니 무인으로 풀어놓을 수 있다.
검증 없이 먼저 무인화하면 조용히 틀린 결과를 매일 생산한다.

**필수 안전장치 2개**

- **중복 등록 방지** — 같은 잡이 두 벌 등록되면 이중 실행 · 이중 과금. 설치 시점에 거부
- **템플릿화** — 감독자 설정에 절대경로가 박히면 환경 이전 시 전부 수동 수정

**0건 산출을 표면화한다** — 예외를 삼키는 핸들러가 있으면 하위 층이 죽어도 경고 한 줄로 묻힌다.
0건은 정상이 아니라 **헬스 경고**로 올린다.

**성공 신호** — 실행 환경이 가용해지기만 하면 아무 명령 없이 밀린 작업이 시작되고,
죽은 워커는 심박 파일로 식별된다.

**일반 이름** — process supervisor · daemon · fault isolation · heartbeat · liveness/readiness · graceful shutdown

---

### 7 · 관측 평면 — Observability Plane

**정의** — 실행 시스템이 남긴 상태를 **읽기 전용으로** 집계해 단일 화면으로 제시하는 계층.

**설계 제약: read-only.** 관측자가 대상 시스템의 상태를 바꾸면 관측값을 믿을 수 없다(observer effect).
계측 코드를 애플리케이션에 심지 않고, 3단계가 남긴 상태 파일만 읽는다.

**왜 이 자리인가** — 6단계에서 워커가 무인으로 돌기 시작하면 아무도 보고 있지 않다.

**관측 대상이 환경에 따라 달라진다**

| 상시 가용 환경 | 간헐 가용 환경 |
|---|---|
| "지금 무슨 일이 벌어지고 있나" | **"내가 없는 동안 무엇이 안 벌어졌나"** |
| 실패 카드가 최상단 | **경과 시간(staleness)이 최상단** |

후자가 더 위험하다. 실패는 로그에라도 남지만 **실행되지 않은 것은 아무 흔적이 없다.**

**핵심 지표** — queue depth · oldest queued job age · heartbeat lag · retry rate · 자원 소진 예측(최근 소비율 외삽).

**성공 신호** — 시스템 앞에 앉은 지 10초 안에 무엇이 밀렸고 무엇이 실패했고 무엇을 판단해야 하는지 안다.

**일반 이름** — observability · control plane vs data plane · observer effect · SLI/SLO · saturation

---

### 8 · 정책 집행 지점 · 안전 장치 — Policy Enforcement Point · Safety Interlock

**정의(전자)** — 모든 행위를 실행 직전에 가로채 `허용 / 거부 / 사람에게 질의` 셋으로 분류하는 단일 통제 지점.

**정의(후자)** — 자동화가 오작동할 때 영향을 제한하는 장치 — debounce · cooldown · manual pause · killswitch.

**왜 이 자리인가** — 7단계에서 무엇이 막혀 있는지 보이게 됐으니 원격에서 그걸 풀 수 있다.

**비동기 승인의 설계 난점 4가지**

1. 집행 지점이 응답을 기다리면 주 실행 경로가 멈춘다 → 즉시 반환하는 비동기 구조
2. 원격 응답을 실행 경로에 어떻게 주입할 것인가
3. **주입 성공 ≠ 실제 처리됨** → 주입 결과를 상태로 검증해야 한다
4. 반복 승인은 룰로 적재되어 쓸수록 질의 빈도가 줄어야 한다

**권한 3등급을 코드로 고정한다**

```
자동 허용   읽기 · 분석 · 지정 영역에 새 파일 생성
사람 승인   외부 발신 · 덮어쓰기 · 대량 처리 · 민감 데이터 접근
영구 금지   임의 명령 실행 · 허용 범위 밖 경로 · 비승인 외부 업로드
```

**안전 장치를 복구보다 먼저 만드는 이유**

- **debounce 없으면** — 일시적 지연을 죽음으로 오판해 살아 있는 프로세스를 죽이고 재시작하는 루프(flapping)
- **killswitch 없으면** — 자동화가 틀렸을 때 사람이 개입할 경로가 없다. 이것이 없는 자동 복구는 **사고 증폭기**다

**성공 신호** — 실행 환경 앞에 없어도 승인이 되고, 파이프라인이 죽으면 사람이 확인하러 가기 전에 알림이 온다.

**일반 이름** — human-in-the-loop · policy enforcement point · capability restriction · flapping · escalation

---

### 9 · 장애 감지와 주입 — Fault Detection · Chaos Injection

**정의(전자)** — 실패뿐 아니라 **부재**를 감지하는 것. "N일 이상 실행되지 않은 파이프라인"을 지표로 다룬다.

**정의(후자)** — 장애를 의도적으로 발생시켜 감지 경로와 대응 순서를 검증하는 것.

**왜 이 자리인가** — 8단계에서 killswitch와 manual pause가 생겼으니 안전하게 장애를 낼 수 있다.
안전 장치 없는 카오스 실험은 그냥 사고다. 순서가 뒤집히면 안 된다.

**주입 목록**

```
API rate limit · timeout · 워커 강제 종료 · 스키마 위반 입력
산출물 누락 · 중복 요청 · 동시 쓰기 · 알림 전달 실패
심박 정지 · 저장공간 부족
```

**실패 모델 표** — 에러 처리에서 실패 **모델링**으로의 이동

```
일시적 자원 부족   → 큐잉 후 재개
외부 API 실패      → 제한된 재시도
잘못된 입력        → 즉시 거부
프로세스 hang      → timeout + 별도 정리자
산출물 누락        → 업무 실패로 판정
승인 불확실        → 사람에게 에스컬레이션
보안 경계 위반     → 실행 중단
```

**런북을 먼저, 자동화는 나중.** 사람이 하는 순서를 문서화한 다음에 자동화한다.
디버깅 순서 자체가 재사용 자산이다.

**성공 신호** — 장애 10종을 일부러 냈는데 전부 감지되고, 각각의 대응 순서가 문서로 남아 있다.

**일반 이름** — partial failure · chaos engineering · staleness detection · runbook · postmortem

---

### 10 · 점진적 롤아웃 — Progressive Delivery

**정의** — 사람 검토를 거치던 행위를 **측정된 신뢰도**에 근거해 단계적으로 자동 실행으로 승격하는 절차.

**승격 게이트** — 무수정 통과율 · 최근 관측 기간 · 최소 표본 수. **표본이 부족하면 승격 불가.**

**왜 이 자리인가** — 9단계에서 실패 목록이 만들어져야 "이건 자동으로 해도 된다"를 숫자로 말할 수 있다.

**필수 장치**

```
영구 금지 목록   선언이 아니라 실행 함수 첫 줄에서 코드로 거부
veto window     실행 예약 → 통지 → 경과 후 실행 (사람이 취소할 창)
일일 상한        초과분은 자동 실행 대신 초안으로 폴백
이상 징후 폴백    해당 건 → 이번 실행 전체 → 기능 자체 비활성 3단계
```

**성공 신호** — 일부 카테고리가 자동 실행으로 승격됐고, 나머지는 왜 승격 못 했는지 숫자로 설명된다.

**일반 이름** — progressive delivery · feature flag · kill switch · blast radius · canary

---

### 11 · 페이브드 로드 검증 — Paved Road Proof

**정의** — 1~10단계가 실제로 재사용 가능한 기반인지를 **새 기능의 리드타임**으로 측정하는 것.

**왜 이 자리인가** — 이건 새 기능이 아니라 **증명**이다.
플랫폼의 가치는 "잘 만들었다"로 주장할 수 없고 다음 산출물의 속도로만 관측된다.

```
첫 번째 산출물:  도메인 + 운영 기반을 함께 만듦
두 번째 산출물:  도메인만 새로 쓰고 운영 기반은 상속
```

**측정 방법** — 착수 전부터 리드타임을 기록하고, "새로 쓴 것 vs 상속한 것"을 표로 정리한다.

**성공 신호** — 새 기능에서 새로 쓴 코드가 도메인 로직뿐이고, 잡 · 게이트 · 검증 · 관측 · 알림은 한 줄도 새로 안 썼다.

**일반 이름** — internal platform · paved road · golden path · lead time

---

### 12 · 운영 이양과 이식성 — Operational Handoff · Portability

**정의** — 시스템을 만든 사람 없이도 운전 · 이전 가능한 상태로 만드는 것.

**산출물** — 파이프라인별 런북 · 설계 결정 기록(ADR) · 인시던트 아카이브 · "수동으로 되돌아가는 법" 문서.

**이식성은 선언이 아니라 측정한다**

```
검증 방법: 깨끗한 환경에서 clone → 설정만 채우기 → 실행
성공하면 다른 머신으로도 이전 가능.
실패하면 어딘가에 절대경로나 환경 종속 시크릿이 남아 있다는 뜻.
```

**그림자 시스템 방지** — 실행 방법이 단순하고, 실패 이유가 보이고, 수동으로 되돌아갈 수 있어야 한다.
시스템이 멈춰도 원래 업무가 죽지 않아야 한다.

**성공 신호** — 처음 보는 사람이 런북만 읽고 시스템을 운전할 수 있다.

**일반 이름** — operational handoff · auditability · backup and restore · shadow IT

---

### 0 · 상시 실행 런타임 ⏸ 보류 — Always-on Runtime · Session Persistence

**정의** — 실행 주체를 로그인 세션의 수명에서 분리해 상시 가용 머신에 상주시키고, 원격에서 접속 · 지시하는 것.

**왜 보류인가** — 상시 가용 머신이 없다. 그리고 이걸 보류해도 1~12가 전부 성립하도록 설계했다 —
가용성 부재를 *구조*가 아니라 *실행 계층*의 문제로 격리했기 때문이다(2단계).

**나중에 도입하면 — 되돌릴 것은 없고 더할 것만 있다**

```
이전 단위 = 프로세스가 아니라 디렉토리     ← 상태가 전부 파일이라서
clone(코드) + rsync(상태) + 환경 재구성 + 감독자 등록
```

| 항목 | 코드 수정 |
|---|---|
| 워커 (드레인 → 상시 실행) | **없음** — 최소 간격 모델이 그대로 동작 |
| 캐치업 드레인 (자주 → 거의 안 함) | **없음** — 죽은 코드가 아니라 안전망으로 남음 |
| 관측 평면 (재진입 브리핑 → 상시 대시보드) | **없음** — 같은 상태 파일을 읽음 |
| 자동 복구 (self-healing) | **추가** — 그때 비로소 의미가 생김 |
| 원격 세션 접속 | **추가** |

**일반 이름** — session persistence · detached process · terminal multiplexer

## 5. 환경 제약과 실행 계층

상시 가용 머신이 없다. 이것은 결함이 아니라 **모델링해야 할 조건**이다.

> 실패를 정상 상태로 모델링하는 것과 같은 방식으로, **가용성 부재를 정상 상태로 모델링한다.**

| 계층 | 성격 | 무엇이 들어가나 | 판단 기준 |
|---|---|---|---|
| **A** | 상시 | 외부 CI 등 상시 실행기 | 하루 끊기면 **영구 손실**이고, 자격증명이 필요 없는 것만 |
| **B** | 기회주의 | 로컬 감독자(launchd) | 자격증명이 필요한 나머지 전부. 가용해질 때 드레인 |
| **C** | 사람 | 승인 채널 | 판단과 비가역 승인 |

**계층 A 판단 기준이 좁은 이유** — 외부 실행기에 회사 자격증명을 올리는 순간
시크릿 경계가 조직 밖으로 나간다. Δ 연속성이 필수이면서 공개 데이터인 것만 A에 둔다.

**계층 C는 미완성이 아니라 설계된 상한이다.** 시스템 목표는
**"실행 노동 0, 판단 시간만 남김"** 이고, 그 판단조차 시스템이 큐로 정리해 올리는 것까지가 범위다.

## 6. 불변 규칙

전부 실제 사고에서 도출됐다. 새로 발명한 것이 아니다.

| # | 규칙 | 근거 |
|:--:|---|---|
| 01 | 컷오버 전에 신 · 구를 동시에 돌리지 않는다 | 외부 상태(큐 · 커서 · DB)를 물리적으로 공유하면 중복과 누락이 난다 |
| 02 | 게이트(실행 전)와 차단선(이미 소비)을 합치지 않는다 | 추정 오차만으로 전체가 0건이 된다 |
| 03 | 비가역 연산에 보수적 | false merge는 비가역, 중복은 가역. 애매하면 자르지 말고 판단에 위임 |
| 04 | 수집 계층은 품질을 판단하지 않는다 | 양 · 신선도 경계는 수집이, 품질은 판정자와 사람이. 섞으면 근거 없이 후보가 사라진다 |
| 05 | 반환값을 믿지 않고 상태를 관측한다 | 보냈다 ≠ 처리됐다 ≠ 저장됐다 ≠ 전달됐다 |
| 06 | 실패를 삼키는 예외 처리를 두지 않는다 | 경고 한 줄이 수백 줄에 묻혀 하위 층이 엿새간 죽어 있었다 |
| 07 | 판단은 세어서 한다. 샘플로 하지 않는다 | 기저율이 낮으면 소표본 0건은 흔한 사건이다. 누적 n으로 판정 |
| 08 | 자동 복구보다 오작동 방지를 먼저 만든다 | debounce · cooldown · manual pause · killswitch가 self-heal보다 앞선다 |

## 7. 자가 점검 — 8개 질문

새로운 자동화나 기능을 설계할 때 **먼저** 묻는다. 답하지 못하는 항목이 곧 그 시스템의 빈 층이다.

```
1. 이 작업의 상태는 어디에 남는가?
2. 성공은 무엇으로 검증하는가?
3. 중간에 죽으면 어디서 재개하는가?
4. 동시에 실행되면 무엇이 충돌하는가?
5. 공유 자원은 누가 조율하는가?
6. 관측 가능하지 않은 실패는 무엇인가?
7. 외부 입력이 실행 권한으로 넘어가는 경로는 없는가?
8. 이 해결책을 다음 산출물에서도 재사용할 수 있는가?
```

**사고의 세 가지 이동**

```
기능 중심   →  상태 중심      전이마다: 누가 바꾸나 · 어디 기록되나 · 중복 가능한가 · 죽으면 남나
에러 처리   →  실패 모델링     "터지면 뭘 할까"가 아니라 "어떤 종류의 실패가 있고 각각을 무엇으로 취급할까"
자동화     →  운영체계        Execution · Control · State · Observation · Recovery
```

## 8. 학습 루프

이 문서는 **③의 산출물**이다. 이론을 먼저 다 읽는 방식은 ③을 건너뛰기 때문에 남지 않는다.

```
① 실제 문제를 만난다
② 임시 해결을 한다
③ 문제의 일반 이름을 찾는다     ← 이 문서
④ 이론을 공부한다
⑤ 구조적 해결로 다시 구현한다
⑥ 테스트와 런북으로 남긴다
```

**매주 남길 것** — ADR · 인시던트 리포트 · 런북.

**사람이 직접 결정해야 하는 것** — source of truth · 성공 조건 · 상태 전이 · 권한 경계 ·
복구 정책 · 동시성 상한 · build vs buy. 이것들은 위임하지 않는다.

## 부록 A. 원 덱과의 대응

원 덱의 순서는 발표자 환경의 병목 순서다. 우리 순서는 우리 조건에 같은 사고를 적용한 결과다.

```
덱:   1 상주 → 2 승인 → 3 워커 → 4 관측 → 5 복구 → 6 제품 → 7 파이프라인 → 8 게이트 → 9 상속
우리: 9 → 8 → 3전반 → ★신설 → 7 → 3후반 → 4 → 2+5전반 → 5후반 → ★신설 → 9증명 → 이양
```
