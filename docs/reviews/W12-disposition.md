## 2. 근원 7계열

각 계열은 `설계이탈`(정본대로 안 지음) · `설계결함`(정본 자체가 틀림) · `설계미구현`(정본이
정한 적 없음)으로 분류한다. 이 3분류가 재빌드 여부를 가른다 — **설계결함만이 재빌드 후보다.**

### ① 관문이 자원이 아니라 호출부에 붙어 있다 — `설계이탈`

> ADR 0002 결정 ②("결정 지점을 하나로")를 claude 축에만 이행했다.

| 증거 | 실측 |
|---|---|
| Apify 지출 경로 | `run_actor` 호출 **23곳 / 13파일** 중 `gate.check("apify")` 는 **1곳**(`pipeline.collect`) |
| `_note_fetch`(수집 건강 계측) | 착지 4어댑터 중 **appstore 1개만** 호출. threads(7개 층)·linkedin(4곳) 0회 |
| `core/llm.py` API 경로 | `judge_job` 은 4겹 게이트, 이 경로는 **0겹** — 상한·장부·계측 전부 없음 |
| `resources` 선언 | `tasks.yaml` 선언을 읽는 프로덕션 코드 **0건**. 잡 소스에 하드코딩 |

**왜 이게 한 뿌리인가**: 넷 다 "부르는 걸 잊을 수 있는 자리"에 가드가 있다. 어댑터를 하나 더
쓰면 계측이 빠지고, 도구를 하나 더 만들면 예산이 빠진다. 고칠 때마다 새 구멍이 생기는 형태(④).

**처방**: 가드를 **chokepoint 로 내린다**. `gate.check` 와 `_note_fetch` 를 `apify.run_actor`
진입부로, 나머지 게이트는 그 자리를 잃는다. `session.py` 가 claude 에 대해 이미 한 것과 같다.
→ **재빌드 아님. 구조 변경이지만 국소적이고 가역이다.** (§4-1)

부분 이행: `bplan-score` 의 `resources` 는 `d706419` 에서 채웠고, 선언↔인자 대조기(C4)를 붙였다.

### ② 단위가 자원과 안 맞는다 — `설계결함` (**최대 계열 · 재빌드 근원**)

> 이번 감사에서 가장 많이 나온 형태이자, 유일하게 **재빌드로만 닫히는** 계열.

| 무엇 | 코드가 세는 단위 | 실제 자원의 단위 |
|---|---|---|
| Apify 지출 계상 | 200 응답 | **런 시작**(타임아웃·429 는 $0 으로 기록되는데 과금은 된다) |
| threads 팔로잉 커서 | `picks` 전량 | **응답을 실제로 받은 픽**(12/20 실패해도 20 전진) |
| `last_run_health.json` | 파일 1개 | **채널 N개**(링크드인 수동 성공이 앱스토어 크론 전멸을 덮는다) |
| 착지 커밋 게이트 | 실행 전체 | **채널**(링크드인 1건 실패로 앱스토어 기준선 동결) |
| `sync_ledger` 멱등키 | `str(행 서수)` | **회사**(시트에 행 하나 삽입되면 다른 회사를 "이미 등록됨"으로 스킵) |
| `drop_ledger` 멱등키 | `page_id` | **사람**(같은 창업자 재접수 5행 → 초안 5통) |
| `heavy_slot` 락 | 자원 이름 | 막아야 하는 건 **같은 잡의 이중 실행**(resources 없는 잡은 무방비) |
| `cursor.json` | 잡 전체 | **스테이지**(전 스테이지 `item_done` 을 한 집합으로 접는다) |

**왜 재빌드인가**: 위 8개는 "조건을 하나 더 본다"로 안 닫힌다. **키를 무엇으로 잡을지**가
틀렸으므로, 키를 바꾸면 그 키를 쓰는 장부·커서·복구 경로가 전부 따라 바뀐다.
특히 아래 두 개는 자료구조를 바꿔야 한다:

- `bplan` sync/drop 의 장부 2종 — 키를 서수/page_id 에서 **불변 식별자**로
- `last_run_health.json` — 파일을 채널별로 쪼개고 `health.compute` 가 task 의 채널을 지목

**정본 대조**: `job.py:56` 은 멱등 키를 *"고유·불변·정확"* 으로 요구하고 `:41` 은 *"퍼지 매칭은
키가 아니다"* 라고 못박았다. 행 서수는 셋 다 아니다. 즉 **플랫폼의 규약은 옳고, bplan 이 그
규약 밖에서 자기 규약을 만들었다.** → §3-A 재빌드.

### ④ 0 이 두 뜻인데 하나만 본다 (진공 ≠ 결손) — `설계미구현`

정본 R5 가 원칙을 세웠으나 **레코드 수 축에만** 구현했다. 다른 축은 비어 있다.

- **컷 사유의 분포** — `_dump_cut` 은 `Counter.most_common()` 이라 사유가 0건이면 **줄 자체가
  사라진다.** "대기업컷 0건"과 "룰이 죽었다"가 출력상 같다. A-F1 이 8일간 안 보인 직접 원인.
- **계측의 부재 자체** — `if att and fail:` 은 `_note_fetch` 를 안 부르는 어댑터를 원리적으로
  못 본다. 유료 2채널이 전멸해도 `✅ collect threads: 0건` + exit 0.
- **0건 export** — `bplan-score` 는 `if not rows: return` 조기 반환이라 진공 가드에 도달하지
  않는다. 08-12 실행은 0건 처리 + ✅ + 무알림 + 워터마크 전진. **매일 반복 중.**
- **경보 임계가 절대값** — 스레드 인물키 경보는 `n_threads == 0` 일 때만 운다. 238명 중 5명만
  못 잡히면 침묵하고 그 5명은 매일 새 행을 만든다.

**처방**: 기대 사유 집합을 들고 **0건인 사유를 명시 출력**. 임계를 절대값에서 **비율**로.
정본 R5 의 문장이 이미 답을 적어놨다 — *"임계가 규모를 타면 그 자체가 결함이다."*
→ 국소 수정 다수. 재빌드 아님.

### ⑦ 룰 문서가 자기를 무효화한다 (판정 품질) — `설계결함` · **별도 트랙**

> 사용자 방침: *"룰 완성되기 전까지는 안 돌린다."* 이 계열은 코드 수정 트랙과 분리한다.

`bplan-criteria.md` 백테스트 실측: 정확도 **64.9%** < 전량-Red 기준선 **73.0%** · 통과 재현율 **44%**.
"왜 기준선을 못 넘나"의 답이 두 개 나왔다.

1. **DQ-1 이 사실상 단독 Red 게이트다.** Red 11건 중 8건이 DQ-1 인용. 임계가 *"6렌즈 중 검증가능
   사실로 선답된 렌즈 4개 이상"* 인데, 판정 입력은 구글폼 서술 9칸이다 — 인바운드 초기 팀이 그
   분량을 적는 일은 구조적으로 드물다. 화해 규칙(*"GD-1 = 정보가 있고 해석이 갈릴 때, DQ-1 =
   정보 자체가 없을 때"*)은 **판별 불가능하다**. 인바운드는 정의상 항상 정보 부족이라 DQ-1 이 항상 이긴다.
2. **프롬프트와 측정 설계가 서로를 무효화한다.** 문서는 "Orange 7% · Red 가 압도적인 것이 정상"
   이라는 사전확률을 주입하면서 동시에 "각 행을 독립적으로 판정하라"고 금지한다. 그런데 백테스트
   표본은 통과 라벨을 전량 실어 **배치 안 통과율이 ~20%**(실분포의 3배)다. 판정자는 7% 를 기대하도록
   프롬프트돼 있다 → 층화 표본에서 구조적으로 통과를 과소 예측한다.

부수: `CR-2b`(TAM 하드캡)는 프롬프트에 없는 모수를 요구해 **인용 0건**으로 사문 · `OG-1` 은 양방향
예외로 어느 결론도 강제하지 않아 모델이 사전확률(=Red)로 후퇴 · `?`(라우팅)가 실산출의 25%인데
백테스트가 **원리적으로 못 잰다**(정답 `?` 인 행을 표본에서 제외).

**처방 순서**: 룰 문장을 깎기 전에 **①캘리브레이션 표를 프롬프트에서 빼고 ②DQ-1 임계를 실측으로
다시 잡고 ③층화/무작위 두 벌을 나란히 보고**한다. 이 셋을 먼저 정렬하지 않으면 룰을 아무리
고쳐도 숫자가 안 움직인다.

## 3. 재빌드가 필요한 것 — 2개

### A. `bplan` sync/drop (`skills/mail-harness/project/bplan/main.py`, 783줄)

**왜 재빌드인가.** 이 파일은 플랫폼(`kv_core.job`)이 생기기 전에 쓰였고, 그 뒤로 플랫폼이 해결한
문제를 **전부 자기 방식으로 다시 풀었다.** 그 방식이 하나같이 틀렸다:

| 축 | 플랫폼 | `bplan/main.py` |
|---|---|---|
| 멱등 키 | 호출자 지정 · 고유·불변·정확 | **시트 행 서수**(`'5483'`) |
| 장부 | `events.jsonl` append-only · 무한 | json 덮어쓰기 · **500건 절삭** · fsync 없음 |
| 원자적 쓰기 | `atomic_write`(tmp 이름에 pid) | 고정 tmp 이름 → 동시 writer 2개 × 400회에 **예외 21회** |
| 락 | `heavy_slot`·`resource_slots` | **0개**(`threading.Lock` 은 프로세스 간 무효) |
| 부작용 멱등 | 가드 + upsert **두 겹** | 가드 한 겹(노션 `pages` POST 는 upsert 아님) |
| 커서 | events 재생 | 시트 `Setting!A1` — **리포 밖 · 락 없음 · 사람이 편집 가능한 단일 정수** |

그 귀결이 이미 데이터에 있다 — **같은 이메일 2행 이상 23명 / 54행**(한 창업자는 5행, 전부
`To Drop`·`드랍메일=True`). 사람이 그 초안들을 보내면 한 창업자가 드랍 메일을 5통 받는다.
`마들렌호텔` 2행은 아직 `Newly Added` 라 **다음에 사람이 To Drop 으로 옮기는 순간 초안 2벌**이 생긴다.

**⚠️ 이관 방법이 계획과 다르다.** ADR 0004 결정 ①의 shadow 병행은 전제가 **"저장소 분리"**인데,
이 task 의 세 외부 상태(시트 A1 · 노션 DB · Gmail 인박스)는 **물리적으로 공유돼 복제가 불가능**하다.
불변규칙 01(신·구 병행 금지)을 지킨 채로는 shadow 컷오버를 **적용할 수 없다.**

**방법 — "한 번에 하나"(플래그 컷)**

```
0단계  선행 조건: §5 의 A-1 (중복 드랍 선점) 을 먼저 넣는다. 재빌드 전에 출혈을 멈춘다.
1단계  키 설계부터. 시트 응답 ID(또는 이메일+제출 타임스탬프)를 **불변 식별자**로 정하고,
       그 값을 노션 행에 심는다. 기존 519행에 소급 채우는 backfill 을 먼저 돌린다(읽기→쓰기 1칸).
       ★ 이게 재빌드의 실제 임계 경로다. 키가 없으면 그 뒤가 전부 막힌다.
2단계  `bplan_sync_job.py` 를 **새로 쓴다**(기존 파일 수정 아님).
       run_pipeline · events 의 item_done · resources=["sheet-a1","notion-bplan"] ·
       노션 등록 전 멱등 조회(그 키로 이미 있는 페이지) → upsert.
3단계  구 경로를 **읽기 전용으로 강등**(`--dry-run` 강제)하고 신 잡을 하루 돌려
       `events` 와 노션 실물을 대조. 이 창에서만 두 코드가 존재하되 **쓰는 쪽은 하나**다.

       (되돌릴 근거로).
5단계  drop 을 같은 방식으로. 단 멱등 단위는 **이메일**이다(§2-② 참조).
```

**1. dry-run 이 설계를 깼다.** 9-2 는 "커서를 없앤다"로 설계했는데 dry-run 이 신규 36건
대신 **5,033건**을 냈다. 노션이 최근 4.5개월만 담고 있어 "노션에 없다 ≠ 안 넣었다"였다.
그대로 실행했으면 6년치를 쏟아부었다. **연습 없이 프로덕션을 만지지 않는다.**

**2. 검사를 좁힐 때는 근거를 코드에 적는다.** O3 를 `To do` 전면 금지에서 "Newly Added
리터럴만 허용"으로 좁혔다. 근거가 없으면 다음 사람이 되돌리거나 더 넓힌다.

**3. 고칠수록 탐지기가 눈이 머는 형태가 있다.** 노션 도구를 옮기자 URL 리터럴이 사라져
탐지 모집단에서 빠졌다. 검사가 **자기가 유도한 변화에 눈이 머는지**를 봐야 한다.
