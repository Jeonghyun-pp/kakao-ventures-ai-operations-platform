## ① 데이터 구조 스펙 — 설계가 정한 상태 저장 구조

### 1-1. 최상위 3분할 (코드 · 상태 · 비밀)

> `docs/adr/0001-공통-기반을-먼저-뽑는다.md:116-120` — 원문 그대로:
> ```
> ~/kv-automation/   코드    git 관리 · 972MB → 195MB
> ~/kv-data/         데이터   315MB · rsync 단위 · git 명령이 닿지 않는다
> ~/kv-config/       시크릿   .env 1개 + 자격증명 3개 · 권한 600
> ```

왜 셋인가 — **복구 정책이 다르기 때문** (`docs/lessons/W1-공통-런타임.md:46-52`):
코드는 git으로 되돌릴 수 있고, 데이터는 **영구 손실**이며 정기 rsync가 유일한 방어이고,
비밀은 회전(rotate)이 가능하다. 셋을 같이 두면 `git clean -xdf` 한 번에 코드도 데이터도 소실된다
(`docs/lessons/W1-공통-런타임.md:41-44`).

시크릿 디렉토리의 내부 구조는 ADR이 아니라 코드 독스트링에 있다 (`kv-core/kv_core/secrets.py:28-32`):
```
~/kv-config/
├── .env                  600
└── gmail/
    ├── token.json        600   재인증은 여기 하나만
    └── credentials.json  600
```
Keychain을 안 쓴 이유도 같은 곳에 있다 — **머신 종속이라 이전 자체가 불가능해진다**
(`kv-core/kv_core/secrets.py:18-20`, 기본구조 1단계의 비가역 결정 3가지 중 하나 =
`docs/BASIC-STRUCTURE.md:119-123`).

### 1-2. State Plane — 잡 디렉토리 규약 (정본 선언)

**정본 = `docs/BASIC-STRUCTURE.md:172-179`.** 3단계(잡 러너와 상태 프로토콜) 정의 안에 있다. 원문:

```
jobs/<id>/
  request.json    무엇을 요청받았나
  state.json      지금 어느 단계인가
  events.jsonl    무엇을 수행했나 (append-only)
  artifacts/      산출물
  stderr.log
```

같은 규약의 **경로 접두사와 cursor 추가**는 W3-W4 레슨에 있다 (`docs/lessons/W3-W4-상태와-내구실행-회고.md:12`):
```
$KV_DATA/<skill>/jobs/<id>/   request · events.jsonl · state.json · cursor · artifacts
```

**상태 전이** (`docs/BASIC-STRUCTURE.md:182`):
```
requested → queued → running → validating → completed | failed
```
그리고 **전이마다 넷을 정의한다** — *누가 바꾸나 · 어디 기록되나 · 중복 전이 가능한가 · 죽으면 남나*
(`docs/BASIC-STRUCTURE.md:185`).

**강제 사항 2개** (`docs/BASIC-STRUCTURE.md:199-202`):
- **append-only 로그** — 덮어쓰지 않는다. 중단돼도 앞부분이 남는다
- **원자적 쓰기 (tmp → rename)** — 비원자적 쓰기는 재실행 시 중복 산출물을 만든다

**동시성 정책** (`docs/BASIC-STRUCTURE.md:204`): heavy는 동시 1 + 큐, light는 병렬.

**성공 신호** (`docs/BASIC-STRUCTURE.md:207`): 실행 중인 잡을 `kill -9` 해도 상태 디렉토리만 보고
무엇이 어디까지 됐는지 안다.

### 1-3. 파일 3종의 역할 분리 — 합치면 안 되는 이유

`docs/BASIC-STRUCTURE.md:266-274` (6단계 프로세스 감독) 원문:
```
health file  → 지금 살아 있는가       자주 갱신 · 덮어쓰기
event log    → 무엇을 수행했는가      append-only
state file   → 지금 어느 단계인가     전이 시점에만
```
> 셋을 하나로 합치면 안 된다 — **갱신 주기와 쓰기 패턴이 다르다.**

### 1-4. events 가 진실, 나머지는 캐시

`docs/lessons/W3-W4-상태와-내구실행-회고.md:15-17`:
> **events 가 진실, 나머지는 캐시** — state·cursor 는 events 를 재생(fold)한 파생물이다.
> 재개는 언제나 관측된 파일에서 시작하고, 반환값·메모리를 믿지 않는다(규칙 05).
> 일반 이름: event sourcing · materialized view

같은 문서 `:18-20`이 리뷰가 가르친 각주를 달았다: *"깨질 수 있는 건 마지막 줄뿐"이라는 규약은
**append 전에 torn 꼬리를 복구해야만** 참이 된다(선언만으로는 스스로 깨졌다 — H2).*

### 1-5. 워터마크 (cadence 상태) — catch-up 의미론

`config/tasks.yaml:6-7` 이 필드 어휘의 정본이다:
```
catch_up:  coalesce(1회로 합침) | backfill(놓친 만큼 다 채움)          [결정 A]
watermark: last_success(실패면 재시도) | last_attempt(시도했으면 전진)  [결정 B]
```
설계 의도는 `docs/lessons/W3-W4-상태와-내구실행-회고.md:30-32`:
> **catch-up 의미론은 선언이다** — coalesce vs backfill · last_success vs last_attempt 는
> 코드가 아니라 task 별 선언. 리뷰의 각주: backfill 은 **원천이 과거를 다시 줄 때만** 의미가 있다.

**최소 간격 모델(minimum interval)** — `docs/BASIC-STRUCTURE.md:222-228`:
```
버림:  "매일 정해진 시각에 실행"                  ← 절대 시각 기준
채택:  "마지막 실행 이후 N시간 지났으면,           ← 경과 시간 기준
        다음에 가용해질 때 실행"
```
**부수 규칙** (`:230`): 정의되지 않은 주기 이름은 조용히 강등하지 말고 크게 경고한다.

> 🔴 **워터마크 파일의 경로·파일명·필드 스키마는 어떤 설계 문서에도 없다.**
> `first_attempt` 라는 필드명은 `docs/reviews/W9-findings-disposition.md:37`(B-L2)과
> `docs/reviews/W9-redesign-diagnosis.md` R1 절에서 **결함 서술의 부산물로만** 등장한다.
> 즉 이 구조는 설계에서 내려온 것이 아니라 구현에서 올라와 사후에 기술된 것이다.

### 1-6. 계측 장부 — claude 호출 수 (프록시 지표)

**유일하게 문서(설정 파일)가 경로까지 못박은 장부**다. `config/resources.yaml:34-37` 원문:
```
# [W6] claude — 구독(Max x20)이라 $ 이 아니라 **호출 수가 프록시 지표**다(직접 쿼터 계측 API 없음).
# 계측: session.py(단일 통로)가 $KV_DATA/_usage/claude/<UTC날짜>.jsonl 에 1콜=1줄 append.
# 기준일 = UTC(워터마크와 동일) — KST 09:00 에 일일 창이 리셋됨에 주의.
```
그리고 그 계측의 계약(감수하는 오차)은 `docs/adr/0004-무인화의-세-구조-shadow-러너계약-프록시계측.md:41-46`:
> **chokepoint metering**: 단일 통로(session.py)가 유일한 계측 지점 — spawn 전 어드미션
> (`gate.check_calls`), spawn 시도 후 기록(`record_call`, timeout 포함·미spawn 제외).
> 감수하는 것들: 호출당 크기 상이(±오차), check→record TOCTOU(±동시성 콜), UTC 자정 경계(±1).
> 임계는 선언(resources.yaml)이며 `0 = 전면 동결`이다.

임계값 (`config/resources.yaml:39-41`): `daily_calls_warn: 30` · `daily_calls_block: 50`.
예산 축 (`config/resources.yaml:19-28`): `apify.monthly_budget_usd: 29.0` · `warn_at_pct: 80`.

### 1-8. 산출물 검증 계약 (contracts)

`config/contracts.yaml:1-10` 이 스키마의 정본이다. 스테이지마다:
```
on_invalid: halt | quarantine   ← 부작용 가역성으로 고른다(결정 ②)
  halt       = 하나라도 어긋나면 전체 중단(발송 등 비가역 스테이지)
  quarantine = 어긋난 것만 DLQ 격리하고 나머지 진행(판정 기입 등 가역 스테이지)
schema: {필드: {type, required, enum, nonempty}}
min_records: 통과 레코드 최소 기대치 — 0건 성공(진공 통과)을 침묵 실패와 구분한다(규칙05)
```
설계 근거는 `docs/lessons/W5-산출물검증과-claude-p-통로.md:57-69` (검증 실패 정책은
**부작용의 가역성**으로 갈린다 · 이 정책을 코드에 박지 않고 `config/contracts.yaml` 에 선언한다).

### ADR 0003 — AI는 claude -p 구독으로 단일화한다 (2026-08-03)

**결정 4가지** (`docs/adr/0003:31-41`):
> **① 모든 AI 호출을 `claude -p` 구독 세션으로 단일화한다. API 키 의존을 제거한다.**
> `core/llm.py`(API 분류기)는 **은퇴**하고, 사실 분류도 `judge_cli.py` 가 증명한 패턴(export→세션→apply)으로 흡수한다.
> **② 결정론적 통제는 코드, 판단·생성만 claude.**
> **③ claude 구독 = 공유 자원 → 단일 관문.** `tasks.yaml` 에 `claude` 자원 등록 → 세션 직렬화. 게이트를 "$ 과금" 대신 "호출 빈도·쿼터" 감시로 재타깃(W6).
> **④ claude 출력은 강제(hard)가 아니라 권고(soft) → 되읽기 검증 필수.** W5 `validating` 스테이지를 "옵션"에서 **"생명줄"**로 승격.

**대가 4가지** (`docs/adr/0003:81-89`):

| # | 대가 | 원문 |
|---|---|---|
| ① | **무인 실행이 세션 인증에 의존한다** | "API 키(환경변수 한 줄)보다 취약할 수 있다. → W5 선행 스모크 테스트로 먼저 확인. **여기가 최대 리스크**" (`:83`) |
| ② | **구조화 출력의 하드 보장을 잃는다** | `json_schema` 강제가 사라져 되읽기 검증이라는 **상시 비용**이 생긴다 (`:85`) |
| ③ | **쿼터가 새 병목이 된다** | "돈이 안 드는 대신, 많이 쓰면 쿼터가 소진돼 **사람이 claude를 못 쓴다**" (`:87`) |
| ④ | **"우리 머신에서만" 제약** | claude -p 구독은 외부 CI 러너 불가. "claude 판단은 **내부에만 산다**(ADR 0002 신뢰 경계와 정합 — 오히려 강화)" (`:89`) |

**검증으로 기록된 것** (`:69-77`): 무인 인증 스모크 통과(잠금-깨어있음 · sleep-wake 둘 다) ·
합성 수직선 4시나리오 통과 · 진짜 Gmail 초안까지 실배선(생성→read-back→삭제, 인박스 오염 0).
**⚠️ 그리고 스스로를 정정했다** (`:76`): *"스코프 `gmail.modify` 라 API 레벨에서도 send 불가"는
**오류였다** — 무발송의 실 보장은 **"코드에 send 호출이 없다"** 하나이며, 이를 AST 검사가 상시 확인한다
(주장 두 겹 → 검증된 한 겹으로 정정).*

### ADR 0004 — 무인화의 세 구조: shadow 병행 · 러너 성공 계약 · 프록시 계측 (2026-08-05)

이 ADR은 대가 절을 따로 두지 않고 **"이 결정들이 틀렸다면"** 으로 반대급부를 적었다 (`:52-59`).

**결정 ① — 컷오버는 shadow 병행으로 산다** (`:10-22`):
registry 에 `shadow: bool` 을 선언. 외부 러너가 primary 인 task 를 로컬 스케줄러가 검증용으로 병행 실행.
컷오버 = `runner: local` + shadow 제거 — 한 줄.
- **왜 runner 를 거짓말시키지 않나**: runner 는 "실행 주체가 누구인가"의 선언이다.
- **전제 = 저장소 분리**: 같은 저장소면 불변규칙 01(신·구 병행 금지) 위반.
- **프로토콜**: 3일 연속 로컬 성공(유효 파일 ≥80/84) → 컷오버 결정(사람 승인) → 구 러너 은퇴.
- **관측 주의**: shadow 의 워터마크는 **로컬 검증 신호**지 task 건강이 아니다.
- **대가(틀렸다면)**: *"shadow 가 3일 넘게 계속 필요하다 → 컷오버 기준이 틀렸거나 로컬 러너가 신뢰 불가 — shadow 는 전이 상태지 상주 상태가 아니다"* (`:54-55`).

**결정 ② — 러너 성공 계약: True 는 "완주"만 뜻한다** (`:24-35`):
> **러너 = `(task, period) -> bool`, True = 그 주기의 일이 실제로 완주·검증됐다.**
queued(락 경합)·부분 실패·불확실을 True 로 돌려주면 **워터마크가 실행 없이 전진해 결손이 조용히 굳는다**.
의심스러우면 False — **재시도는 싸고, 유실은 비싸다**. 완주 판정은 반환코드가 아니라 산출물이고,
**세는 것은 존재가 아니라 온전함**(0바이트 84개가 통과했다 — 크기>0 + 파싱 가능 + 비어있지 않음).
미배선 task 는 run_due **앞에서** loud 스킵(스킵이 반환값이 되면 last_attempt 오염).
- **대가(틀렸다면)**: *"False 반환이 잦아 재시도가 낭비다 → 완주 판정 임계가 과도 — **임계 재조정(80/84)이지 계약 완화가 아니다**"* (`:56-57`).

**결정 ③ — 계측 불가 자원은 프록시로 재되, 한계를 계약에 적는다** (`:37-48`):
> **게이트의 목적은 정밀 회계가 아니라 방화벽이다** — 재시도 루프 폭주 차단 + 사람 몫 잠식 방지.
> 그래서 **감수하는 것들을 계약에 명시한다** — 호출당 크기 상이(±오차), check→record TOCTOU,
> UTC 자정 경계(±1). `0 = 전면 동결`(falsy 로 "미설정" 취급 금지).
> 분산 불변식(`max_batches_per_run < daily_calls_warn`)은 **기계 검증**한다.
- **대가(틀렸다면)**: *"프록시(호출 수)와 실쿼터 체감이 크게 어긋난다 → 더 나은 대리 지표로 교체 — **계측 지점(chokepoint)은 그대로다**"* (`:58-59`).

**이 ADR 자체가 사후 문서화**임을 첫머리에 적었다 (`:4-7`): 코드 주석·커밋 메시지에만 살던 결정을
승격한 것이고, 근거는 *"의도 문서 없는 주차에 결함이 밀집한다"의 재실증(W3 11건·W4 14건)*.

#### R1 — 파생 상태를 저장한다 (derived state stored)

> **계산할 수 있는 것을 파일에 적어두면, 그 순간 진실이 둘이 된다. 둘은 반드시 어긋난다.**
> (`docs/reviews/W9-redesign-diagnosis.md:44-46`)

**이 원칙을 낳은 실제 사고 2건** (`:48-52`):
- 승인 레코드의 `status`·`sent`·`delivered`·`channel`·`target` 이 전부 다른 필드에서 계산 가능한데 저장돼 있었다.
  그중 **`sent` 는 True 로 만드는 코드가 리포에 없는 죽은 필드**인데 `_is_closed` 가 그것을 보고 있었다.
- 워터마크의 `first_attempt` 가 없으면 `last_attempt` 로 폴백했는데, 그 값은 매일 갱신되므로
  **"배선 후 경과일"이 영원히 0**이 되어 **알림이 영구 침묵**했다.

**처방을 쓰면서 같은 걸 또 만들었고, 실데이터에서 실제로 어긋난 것까지 기록됐다**

### 4-2. 재설계가 확정한 나머지 3원칙 (R 번호는 없으나 같은 문서의 결론)

| 원칙 | 낳은 사고 | 출처 |
|---|---|---|
| **락이 아니라 선점 — 그리고 "누가 푸느냐"** | `decide` 의 first-decision-wins 를 **두 번** 틀렸다: 락을 안 걸면 last-write-wins, 락을 걸면 **유령 락 하나로 승인 전체가 영구 no-op**(A-H3). 셋째 답이 **O_EXCL 결정 마커** — "한 번 생기면 남는 것이 정상이라 stale 회수라는 개념 자체가 없다". 그리고 정말 락이 필요한 자리(`update()` 의 read-merge-write)에서는 **`fcntl.flock`(커널이 소유권 관리 → fd 닫히면 자동 해제)** | `docs/lessons/W9-재설계:111-128` · `docs/reviews/W9-findings-disposition.md:109-113` |
| **관측자를 관측 대상 안에 두지 않는다** | 🔴 stale 판정이 orrery 에만 있었고 orrery 다이제스트는 `scheduler --run` **끝에서만** 나갔다. 스케줄러가 죽으면 `last_attempt`·`last_success` 가 **함께 멈춰 격차가 고정**되므로 알림도 영원히 침묵 — "정상적으로 조용한 날"과 "스케줄러 정지"가 구분 불가. 판정을 `health` 로 빼자 10분 승인 틱이 **스케줄러 밖에서** 본다. **"배치가 문제였지 부재가 문제가 아니었다"** | `docs/lessons/W9-재설계:130-137` |
| **테스트가 선언이 아니라 기억을 지키고 있지 않은지** | **단언 세 개를 뒤집었다.** 예: `_synthetic_alerts` 의 "구 스키마는 폴백으로 미발동이 정답" — 그 폴백이 경과일을 영원히 0으로 만들어 **영구 침묵을 CI 가 보증**하고 있었다. **"계약이 바뀌었는데 테스트가 옛 계약을 지키면 그건 가짜 통과다. 그 테스트는 결함을 막는 게 아니라 결함을 고정한다."** 리팩터 중 빨간 테스트를 만나면 먼저 물을 것은 "코드가 틀렸나"가 아니라 **"이 단언이 아직도 우리가 원하는 것인가"** | `docs/lessons/W9-재설계:139-151` |

**가장 중요한 3개** (감사 분류의 기준이 되는 것):

1. **A9 — ADR 0003 이 "은퇴"라고 선언한 `core/llm.py` 두 벌이 살아 있고 호출부까지 있다.**
   실동작은 `enabled: false` + 키 부재라는 **꺼둠**으로 막혀 있을 뿐이다.
   → 감사 분류상 **"설계 이탈"**(설계가 요구한 최종 상태와 코드가 다름)이며,
   `config.yaml:596-598` 이 스스로 적었듯 **`.env` 에 키 한 줄이 들어가면 상한 없는 API 패스가
   조용히 부활**한다. ADR 0002 대가 ②·ADR 0003 결정 ①이 정면으로 무효화되는 경로다.

2. **D17/D18 — `ledger/*.jsonl` 과 `health/*.json` 은 "안 지어진 것"이 아니라 "설계된 적 없는 것"이다.**
   비용·발송·판정 이력은 실제로는 `_usage/claude/*.jsonl` · `_alerts/sent/<마커>` ·
   `judge_verdicts_*.json` 이라는 **서로 다른 이름·위치·형식**으로 흩어져 있다.
   → 감사에서 이 셋을 "누락"으로 세면 오분류다. 올바른 분류는 **"설계 미비"**(정본 문서가 State Plane
   하위 구조를 `jobs/` 밖까지 규정한 적이 없음)이고, 그 결과가 D11·D14(워터마크·승인 큐의 스키마가
   문서 없이 구현만 존재)로 반복된다.

3. **S3 — `docs/task-registry-mirror.md` 가 사문이라는 사실이 이미 2026-08-05 중간점검에 기록돼 있는데
   그대로다.** 이 문서는 "진실의 출처"를 정의한 유일한 문서이면서 정작 `meeting-mail`·`bplan-score`
   두 task 를 모르고, `bplan` 의 스테이지 구성도 `tasks.yaml` 과 어긋난다.
   → **"정본을 정의한 문서가 정본이 아니다"** 는 R1(파생 상태 저장)의 문서판이다.
   감사에서 나올 문서-코드 불일치는 개별 결함이 아니라 이 한 뿌리로 묶어야 한다.
