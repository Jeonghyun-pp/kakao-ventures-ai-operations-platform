## 0. 두 주를 한 장으로

```
W8  사람의 결정을 시스템 단계로   슬랙 이모지 → 10분 리컨실러 → 라벨 → 실행 → read-back
W9  실패를 초대해서 검정          적대 리뷰 56건 + 장애 주입 7종 + 런북 5본
```

## 1. 조정 루프는 이벤트가 아니라 diff 를 본다 (reconciliation)

승인을 "버튼 클릭 이벤트"로 받으려면 **받는 쪽이 항상 깨어 있어야** 한다(서버). 우리 맥북은
잔다. 그래서 이모지를 **선언**으로 두고, 틱이 깨어날 때마다 선언과 실제의 차이를 메꾼다.

```
desired  슬랙에 ✅ 가 붙어 있다        ← 사람이 남긴 선언(슬랙이 보관)
actual   그 승인건이 아직 실행 안 됨   ← 큐 레코드
tick     10분마다 diff 를 좁힌다       ← 자면 멈추고 깨면 이어감(놓칠 것이 없다)
```

> **일반 이름 — reconciliation loop.** 쿠버네티스가 세상을 움직이는 방식과 같은 모양이고,
> crash-safe 가 공짜인 이유도 같다: 상태가 외부(슬랙·파일)에 있으니 루프는 언제 죽어도 된다.

## 2. 루프의 주기는 "일의 비용"과 "감당할 지연"의 흥정 (fast/slow path)

수거는 API 읽기 1번이라 공짜다. 수집은 84차트라 비싸다. 둘을 같은 리듬에 묶으면 어느 쪽이든
손해다 — **10분 틱(승인)과 4시간 틱(수집)을 분리**했고, idle 틱은 1초에 끝난다(duty cycle).

## 3. 무승인 무실행은 주석이 아니라 **호출 구조**여야 한다

`_execute()` 의 입력이 `approved_unexecuted()` **하나뿐**이면, 승인 없이 실행되는 경로가
구조적으로 존재하지 않는다. 그런데 리뷰가 **두 번째 경로**를 찾아냈다 — `request(live=True)`
가 결정 전에 초안을 만들고 있었다. 원칙을 한 곳에 적어두는 것과, 그 원칙을 어길 문이 없는
것은 다르다.

## 4. 실행 후에도 믿지 않는다 (read-back · compensation)

"만들었다 ≠ 반영됐다" — 초안 id 를 되읽어 확인하고, 실패하면 **결정을 유지한 채** 다음 틱이
재시도한다(보상). 분산 트랜잭션이 불가능한 곳(노션+Gmail+파일)에서 되돌리기는 rollback 이
아니라 보상 액션이다.

## 5. 이번 사이클의 지배적 실패 모드는 **가짜 침묵**이었다

W0-W5 리뷰에서 두 번 덴 것은 "가짜 경보"(테스트가 실 채널에 쏜 경보)였다. 그런데 W8 코드에서
리뷰가 찾은 것은 반대였다:

| 발견 | 실체 |
|---|---|
| 인증 만료가 `ok:true` 로 기록 | rc==0 을 성공으로 봤는데, 이 코드 스스로 "rc0+빈 출력=인증 만료"라 정의했다 |
| 매일 실패하는 judge 가 알림에서 제외 | 내가 "회귀만 알린다"고 좁힌 규칙이 **한 번도 성공 못 한 것**을 온보딩과 같은 통에 넣었다 |
| 보상 재푸시가 실행 불가 | 마커를 먼저 만들고 발송해서, 실패해도 마커가 남아 영원히 재시도 못 했다 |
| 승인 굶주림 | 상한 슬라이스가 필터보다 앞이라 묵은 미결이 슬롯을 먹고 신규가 안 잡혔다 |

**교훈**: 소음을 줄이는 수정은 신호를 죽일 수 있다. "이 알림이 자기 목적 시나리오에서 실제로
울리는가"를 **실험으로 확인**해야 한다 — 그게 E5(인증 만료 시뮬)를 만든 이유다.

## 6. 같은 실수는 같은 모양으로 반복된다 (그래서 테스트가 필요하다)

A-F3(굶주림)을 `_reconcile` 에서 고치면서, **`_announce` 에 같은 구조를 새로 만들었다**
(상한을 필터보다 앞에 둔 것). 테스트가 그걸 잡았다. 그리고 그 수정 과정에서 회전 커서라는
과잉 설계를 넣었다가 동작하지 않아 걷어냈다.

> 수정 중에 새 결함을 심는 것은 예외가 아니라 정상이다. **리뷰-수정-재검증 루프**에서
> 재검증이 없으면 수정은 도박이다.

## 7. 계획된 실패가 계획 안 된 실패보다 싸다 (chaos engineering)

장애 주입 7종을 돌려 안전장치가 **실제 병원체**에 듣는지 봤다. 합성 테스트는 "내가 상상한
실패"만 검증한다. 실험 형식은 매번 같다:

```
정상상태 가설 → blast radius 선언 → 주입 → 관측 → 판정
```

blast radius 를 먼저 적는 것이 chaos 의 제1규율이다. 우리는 유리했다 — **발송 경로가 아예
없어서**(AST 상시검증) 최악이 "초안 중복·알림 오발"로 이미 캡핑돼 있었다.

## 8. 자동화 전에 사람 절차부터 (runbook-first)

런북 5본을 썼다. MTTR 을 "그때 생각해서"가 아니라 **읽고 따를 수 있는 절차**로 고정하면
대응 시간의 상한이 생긴다. 그리고 무엇을 자동화할지는 실측 빈도가 정한다 — 3일간 실제로
일어난 실패는 망 단절과 빈 응답 둘뿐이었고, 둘 다 이미 자동 처리된다.

## 가져갈 것 — 8줄

```
1. 조정 루프는 이벤트가 아니라 diff 를 본다          (reconciliation · crash-safe 가 공짜)
2. 루프 주기 = 일의 비용과 지연의 흥정               (fast/slow path · duty cycle)
3. 무승인 무실행은 호출 구조로 보장한다              (single entry · 두 번째 문을 찾아라)
4. 실행 후에도 되읽는다, 실패는 보상한다             (read-back · compensation · saga)
5. 소음을 줄이는 수정이 신호를 죽일 수 있다          (가짜 경보 ↔ 가짜 침묵)
6. 알림은 자기 목적 시나리오에서 울려야 한다          (alarm testing · MTTD)
7. 계획된 실패가 계획 안 된 실패보다 싸다            (chaos · blast radius 선언)
8. 자동화 전에 절차, 자동화 대상은 빈도가 정한다      (runbook-first · MTTR 상한)
```
