## 0. W1을 한 장으로

```
[전]  앱 6개가 각자 모든 걸 들고 있음
      ┌────────┐ ┌────────┐ ┌────────┐
      │ 코드    │ │ 코드    │ │ 코드   │
      │ 시크릿  │ │ 시크릿  │ │ 시크릿 │   ← 같은 값이 3벌
      │ 데이터  │ │ 데이터  │ │ 데이터 │   ← 리포 안
      │ 런타임  │ │ 런타임  │ │ 런타임 │   ← venv 5벌

[후]  관심사별로 층을 갈랐음
      ┌─────────────────────────────┐

           ↓              ↓
```

일반 이름: **separation of concerns** · **stateless code / stateful storage 분리** ·
**internal platform**

## 1. 코드 · 상태 · 비밀은 물리적으로 분리한다

**일반 개념 — blast radius(폭발 반경) 격리.** 한 번의 사고가 어디까지 번지나.

```
같이 두면   git clean -xdf 한 번 → 코드도 데이터도 소실
            실수로 커밋 한 번    → 개인정보가 히스토리에 영구 기록
분리하면    git 명령의 사정권 = 코드뿐. 데이터 사고 ≠ 코드 사고
```

**왜 셋인가 — 복구 정책이 다르기 때문이다.**

| | 잃으면 | 복구 | 백업 주기 |
|---|---|---|---|
| 코드 | 되돌릴 수 있음 | git | 커밋마다 |
| 데이터 | **영구 손실** | 없음 | 정기 rsync |
| 비밀 | 재발급 가능 | 회전(rotate) | 거의 안 바뀜 |

데이터 레이크에서 raw/staging/curated 를 물리적으로 가르는 이유,
DB 백업과 코드 배포를 따로 관리하는 이유와 같다.

---

## 2. 규칙은 선언이 아니라 구조로 강제한다

**일반 개념 — enforcement point(집행 지점)를 어디 두나.**

```
선언(convention)    문서·설정에 "하지 마세요"          → 사람이 지켜야 하고 도구가 안 볼 수 있다
구조(structural)    물리적으로 불가능하게              → 지키고 말고가 없다
```

| 선언 | 구조 |
|---|---|
| `.gitignore` 에 `data/` | 데이터를 리포 **밖으로** |
| SKILL.md 에 "콜드 스탠바이" | 심볼릭 **링크 제거** |
| 문서에 "자동발송 금지" | 발송 함수 **첫 줄에서 거부** (W10) |

**선언의 진짜 문제는 틀렸을 때 신호가 없다는 것이다.**
`.gitignore` 는 커밋을 막지만 삭제는 못 막는데, 그걸 알려주는 건 아무것도 없다.

> 제약은 스키마에, 검증은 파이프라인에. 문서에 적힌 규칙은 규칙이 아니다.

---

## 3. 제네릭 계층과 도메인 계층 사이에 선을 긋는다

```
┌──────────────────────────────┐
│ 도메인   "우리 DB를 다루는 법"    │  조직마다 다름
│  DB 라우팅 · 착지 키 · 매핑       │
├──────────────────────────────┤
│ 제네릭   "API를 안전하게 부르는 법" │  누가 써도 같음
│  인증 · 재시도 · 절단 · 스키마 조회  │
└──────────────────────────────┘
```

**판별 질문 — "다른 팀이 다른 DB로 이 코드를 쓸 수 있나?"**
예 → 제네릭 / 아니오 → 도메인.

ETL의 커넥터(제네릭)와 변환 로직(도메인) 경계와 같다.
Airbyte 커넥터가 스키마 매핑을 안 하는 이유.

## 4. 의존은 단방향. 순환 금지

```
나쁨   A ←→ B        서로 참조. B를 지우면 A가 깨진다
좋음   A → core ← B   공통 계층만 거친다. B를 지워도 A는 산다
```

**실제로 터질 뻔한 것** — `ai-consumer-pulse` 가 `hello-mail` 의 토큰을 절대경로로 읽고
있었다. 그 스킬을 아카이브하는 순간 **다음 실행에서 조용히 실패**했을 것이다.

데이터 파이프라인 DAG에 순환이 있으면 안 되는 것과 같은 원리다.

---

## 5. 설정은 네 가지로 나눈다

12-factor는 코드/설정 둘로 나누지만 실무엔 넷이 있다.

| | 판별 | 유출되면 |
|---|---|---|
| ① 시크릿 | 남이 나로 행세할 수 있나 | 회전(rotate)하면 끝 |
| ② 설정 | 환경마다 값이 다른가 | 무해 |
| ③ **판단 기준** | 값이 바뀌면 *결과*가 바뀌나 | **회전 불가. 조직의 노하우** |
| ④ 실데이터 | 외부인 정보·기밀인가 | **회전 불가. 끝** |

**③이 12-factor 밖에 있다.** 심사역 명단·칼드랍 기준·담당자 태그가 여기 속하고,
org 이관 논의의 실제 대상이기도 하다("private이어도 개인 계정이면 문제"가 성립하는 이유).

각각 **보관 위치·백업·접근 통제가 달라야** 한다. 섞으면 가장 엄격한 정책을 전부에
적용하거나(비효율) 가장 느슨한 정책이 새어나간다(사고).

---

## 6. 참조 데이터와 테스트 픽스처는 다르다

```
테스트 픽스처   코드 검증용. 구조만 필요, 값은 무의미해도 됨   → 익명화 가능
참조 데이터     사람이 대조용. 실물이어야 함                  → 저장소 밖
지식           이미 코드로 옮겨진 것                        → 주석·문서
```

**한 파일이 세 역할을 겸하고 있으면 결정이 안 된다.** 분해하면 각각 갈 곳이 자명해진다.

정답을 이미 실천하고 있었던 사례: `irr_calc.py` 가 엑셀 수식을 주석으로 옮겨 적어
원본 없이도 이해되게 만들어 뒀다. **이게 실물 의존을 끊는 표준 방법**이다.

프로덕션 데이터로 테스트하지 말고 합성 픽스처를 쓰라는 규칙과 같다.

---

## 7. 환경 정본은 하나

```
[전]  requirements 6개  → "어느 게 진짜지?"
      실제로 하나를 빠뜨려 스킬이 통째로 안 돌았다
[후]  리포 루트 requirements.txt 가 정본
      스킬별 파일은 "무엇이 필요한가"의 기록으로만
```

**정본이 여러 개면 하나를 빠뜨려도 아무도 모른다.**
"내 로컬에선 되는데"의 원인이 정확히 이것이다.

---

## 8. 마이그레이션에는 롤백 창이 있다

```
1 병행 준비   신·구 공존, 구가 정본
2 차단       구를 실행 불가능하게 (지우지는 않음)   ← W1에서 여기까지
3 컷오버     신이 정본. 롤백 창 열림                ← W5
4 정리       롤백 창이 닫힌 뒤 구 제거
```

**차단이 삭제보다 먼저인 이유** — 롤백 절차가 구 시스템의 존재를 전제한다.

**같이 배운 위험 — dual-write hazard.** 신·구가 같은 외부 상태(인박스·시트 커서·DB)를
공유하면 병행 실행이 중복과 누락을 만든다.

---

## 9. 인터페이스는 소비자가 검증한다

**consumer-driven contract.**

```
공급자 검증   "우리 API 잘 만들었어요"  → 자기 코드라 안 맞아도 모른다
소비자 검증   실제로 쓰는 쪽이 써본다    → 어색한 부분이 드러난다
```

추출은 원산지에서 하되 **인터페이스 확정은 남의 코드가 써본 뒤에** 한다.
그리고 **가장 많이 요구하는 소비자**로 검증한다 — 적게 쓰는 걸로 하면 절반만 검증된다.

---

## 10. 되돌리기 쉬운 쪽을 고른다

**one-way door / two-way door.**

| 결정 | 근거 |
|---|---|
| 판단 기준을 config에 커밋 | 코드→config는 어렵고, 추적→비추적은 쉽다 |
| 콜드 스탠바이는 아카이브 | 삭제는 롤백 창을 닫고 아카이브는 안 닫는다 |
| 히스토리를 푸시 전 정리 | 푸시 후엔 되돌릴 수 없다 |

# 실수 7건 — 각각의 일반 실패 유형

**가장 실전적인 부분이다. 다음에 같은 모양이 오면 알아보기 위해 적는다.**

| # | 무슨 일 | 일반 이름 | 교훈 |
|---|---|---|---|
| 1 | 잡 이름이 비슷해 "중복"이라 단정 | inference from labels | 이름은 메타데이터다. 동작은 열어봐야 안다 |
| 2 | `parents[3]` 경로 깊이 오산 | 미검증 계산 | 경로 계산은 실행해서 확인 |
| 3 | venv 삭제로 크론 2개 파괴 | 참조 카운트 미확인 | 지우기 전에 "뭐가 이걸 가리키나"를 센다 |
| 4 | requirements 누락 → 스킬 불능 | incomplete dependency closure | 정본이 여러 개면 하나를 빠뜨린다 |
| 5 | 검증 스크립트 버그로 오탐 | instrument error | 놀라운 결과 = 도구를 먼저 의심 |
| 6 | 실패한 명령을 "✅ 0건"으로 읽음 | **silent failure** | 아래 참조 |
| 7 | 측정 없이 "빨라졌다" 보고 | unmeasured claim | 숫자 없는 개선 주장은 인상이다 |

## 6번을 따로 적는 이유

```bash
grep -c "패턴" file | head -5 || echo "✅ 0건"
                      ↑ head 가 성공하면 || 는 안 돈다
```

**시크릿 스캔에서 이게 났다.** 명령이 실패했는데 화면엔 통과로 찍혔다.
그대로 푸시했으면 **검증 없이 나갔다는 사실조차 몰랐을 것이다.**

불변 규칙 05 그 자체다 — **exit 0 ≠ 검사를 수행했다.**

데이터 파이프라인의 같은 패턴: "0건 처리"를 성공으로 리포트하는 잡.
소스가 비어서 0건인지, 쿼리가 틀려서 0건인지 구분 못 하면 조용히 며칠을 날린다.

# 가져갈 것 — 8줄

```
1. 코드 · 상태 · 비밀은 물리적으로 분리한다        (blast radius)
2. 규칙은 선언이 아니라 구조로 강제한다            (enforcement point)
3. 제네릭과 도메인 사이에 선을 긋는다               ("남이 쓸 수 있나?")
4. 의존은 단방향. 순환 금지                       (DAG)
5. 설정은 4분류. 각각 보관·백업이 다르다            (classification)
6. 환경 정본은 하나                               (reproducibility)
7. 지우기 전에 롤백 창이 닫혔는지 본다              (cutover)
8. 검사가 실제로 돌았는지를 검사한다                (silent failure)
```
