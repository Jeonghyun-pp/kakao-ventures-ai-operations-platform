# W6-W7 에서 배운 것 — 무인화 · 관측 · 그리고 패턴은 구조로만 막힌다

> 2026-08-05 · 데이터 엔지니어링 · 구조 설계 관점
> 결정의 이유는 `docs/adr/0004`, 중간점검 전문은 `docs/reviews/W6-W7-midpoint-review.md`.

---

## 0. 두 주를 한 장으로

```
W6  스위치를 켰다   launchd → scheduler --run → 배선 2 task 무인 완주 · 미배선 loud 스킵
W7  눈을 달았다     orrery = 약속(cadence) vs 실제(워터마크) 를 한 판으로 — absence 감지
그리고 중간점검     살아있는 시스템 실측 + 적대 리뷰 → 43건 · "백신 맞고도 4개 패턴 재발"
```

## 1. 트리거는 대충, 의미론은 정확 (pull scheduling)

발화 시각(09:00·4h 보조)이 어긋나도 아무 문제가 없다 — 정확성은 트리거가 아니라
**워터마크 + catch-up 의미론**이 보장한다. 실측: 05:10 발화를 놓친 날, 다음 발화가
84차트를 알아서 채웠다. cron 의 "놓친 tick = 영구 소실"을 pull 이 구조로 없앤다.

> 일반 이름 — **pull-based scheduling · misfire policy · watermark**

## 2. 시작이 곧 복구다 (crash-only design)

스케줄러는 "내가 어떻게 죽었나"를 묻지 않는다 — 깨어나서 선언(cadence)과 기록(워터마크)만
보고 이어간다. 정상 종료 경로가 아예 없는 설계가 오히려 튼튼하다.

## 3. 부재는 diff 로만 잡힌다 (absence detection)

한 일은 로그가 있고 실패한 일은 에러가 있지만, **안 한 일은 아무것도 없다** — "로그가
없다는 로그는 없다". 유일한 방법은 약속(선언된 cadence)과 실제(워터마크)의 차이.
W2 침묵 사고(4일 무감지)의 구조적 해법이고, 선언이 없으면 부재 감지도 없다 —
**선언적 카탈로그는 관측의 전제 조건**이다.

> 일반 이름 — **staleness/freshness · declared expectation vs observed state**

## 4. 관측은 상태를 바꾸지 않는다 — 그리고 그 계약도 기계로 지킨다

orrery 는 read-only 라고 **선언**했지만, 첫 검증에서 mkdir 부작용이 두 번 잡혔다
(`paths.data` 의 create=True 기본값, approval.pending 의 큐 생성). 선언은 지켜지지 않았고,
**AST 상시 검증**(쓰기 호출 0건 단언)을 붙인 뒤에야 계약이 됐다.

> 일반 이름 — **read-only observer · machine-enforced contract**

## 5. 검증은 존재가 아니라 온전함을 잰다

"84개 파일이 있다"는 검증이 0바이트 84개를 통과시켰다(중간점검 T4 실증). 세는 것(규칙 07)
만으로는 부족하고 **무엇을 세는가** — 크기·파싱·비어있지 않음 — 가 검증의 실체다.
"exit 0 ≠ 성공"의 다음 단계: **"파일 존재 ≠ 데이터 존재".**

## 6. 이번 사이클 최대 교훈 — 패턴은 기억으로 못 막는다

W0-W5 리뷰의 5패턴(stdout 침묵·주장vs실체·동시성·진공 통과·falsy)을 **알고** W6-W7 을
빌드했는데 4개가 재발했다. 아이러니의 정점: judge "가동 스위치" 안내문이 마커를 재인용해
스위치가 영영 안 열렸다(T1) — "주장 vs 실체"를 설명하는 문장이 그 패턴의 사례가 됐다.

빌더의 손은 아는 실수를 또 한다. 파인더(적대 리뷰)는 잡지만 리뷰는 이벤트다 —
**상시로 지키는 것은 구조뿐**: AST 검증, 기계 불변식(`max_batches < warn`), 단독 줄
토큰 매칭, `is None` 규율. "선언이 아니라 구조로"의 세 번째, 가장 비싼 재확인.

## 7. 병목이 옮겨간 순간을 알아본다

중간점검 감사의 결론 — "시스템이 사람을 기다리는 상태지, 그 역이 아니다."
엔지니어링이 병목이던 프로젝트가 W6 에서 **도메인 지식(judge 룰)이 병목**인 상태로
넘어갔다. 이 전환을 인지하는 것 자체가 설계의 성공 지표다: control plane 은 완성되면
조용해지고, 남는 입력은 사람만 아는 것이어야 한다.

## 가져갈 것 — 7줄

```
1. 트리거는 대충, 의미론은 정확               (pull · watermark · catch-up)
2. 시작이 곧 복구다                           (crash-only)
3. 부재는 선언과 관측의 diff 로만 잡힌다       (absence detection — 선언이 관측의 전제)
4. 관측은 상태를 안 바꾼다 — 계약은 기계로     (read-only observer · AST enforcement)
5. 존재를 세지 말고 온전함을 세라              (integrity ≠ existence)
6. 패턴은 기억이 아니라 구조로 막는다          (builder ≠ finder · machine-enforced)
7. 병목이 코드에서 사람 지식으로 옮겨가면 성공  (control plane 완성의 신호)
```
