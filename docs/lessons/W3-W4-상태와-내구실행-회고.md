# W3-W4 에서 배운 것 (회고) — 상태를 파일로 · 끊겨도 이어간다

> 2026-08-05 사후 작성. W3(잡 러너·상태규약)·W4(registry·durable execution)는 당시 레슨을
> 안 남겼고, W0-W5 적대 리뷰에서 **결함 최다 주차(11건·14건)가 정확히 이 두 주**였다 —
> "의도 문서가 없는 곳에서 구현이 갈라진다"의 실증. 늦었지만 의도를 여기 고정한다.

---

## W3 — 상태를 파일로 (durable state)

```
$KV_DATA/<skill>/jobs/<id>/   request · events.jsonl · state.json · cursor · artifacts
```

1. **events 가 진실, 나머지는 캐시** — state·cursor 는 events 를 재생(fold)한 파생물이다.
   재개는 언제나 관측된 파일에서 시작하고, 반환값·메모리를 믿지 않는다(규칙 05).
   > event sourcing · materialized view
2. **append-only + 원자적 쓰기** — 덮어쓰지 않으면 크래시가 과거를 못 지운다. tmp→fsync→rename.
   리뷰가 가르친 각주: "깨질 수 있는 건 마지막 줄뿐"이라는 규약은 **append 전에 torn 꼬리를
   복구해야만** 참이 된다(선언만으로는 스스로 깨졌다 — H2).
3. **멱등 키 + 부작용 먼저, 커서 마지막** — 재개가 두 번 불러도 결과는 한 벌.
   kill -9 를 어디서 맞아도 잡 디렉토리만 보고 이어간다(실증됨 — 단, 리뷰가 validating
   전이 구멍을 찾았다: **상태기계의 "모든" 상태에 재개 경로가 있어야** 한다, H1).

## W4 — 끊겨도 이어간다 (durable execution + 선언적 카탈로그)

1. **카탈로그와 실행의 분리** — tasks.yaml 은 "무슨 일이 있나"(선언), 스케줄러는 "지금 뭘
   돌리나"(판정), 러너는 "어떻게 도나"(실행). 이 3분리가 이후 모든 확장(shadow·runner
   필드·loud 스킵)의 문법이 됐다. > declarative orchestration
2. **catch-up 의미론은 선언이다** — coalesce(합쳐 1회) vs backfill(놓친 만큼) · last_success
   (실패 재시도) vs last_attempt(시도로 전진)는 코드가 아니라 task 별 선언. 리뷰의 각주:
   backfill 은 **원천이 과거를 다시 줄 때만** 의미가 있다(appstore 는 안 준다 → coalesce).
3. **공유 자원은 이름 정렬 락** — 데드락은 순서 규약으로 죽는다. stale 회수는 unlink 경쟁이
   아니라 rename(원자적 소유권 선점)으로(D4에서 배움).
4. **승인 브릿지 = 비가역 앞의 사람 관문** — 초안까지만, 발송은 사람. W8 의 토대.

## 이 회고의 진짜 교훈

**의도를 코드에만 두면, 의도가 리뷰어(미래의 나 포함)에게 전달되지 않는다.** W3-W4 의
설계는 대부분 옳았다 — 그런데 문서가 없어서 "옳은 의도의 빈틈"(전이표 누락·torn 규약의
자기모순·backfill 의 전제)을 아무도 대조하지 못했고, 그 빈틈이 25건의 결함으로 돌아왔다.
ADR·레슨은 회고 문서가 아니라 **리뷰의 대조 기준(oracle)**이다.
