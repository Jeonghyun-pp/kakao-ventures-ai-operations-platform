# ADR 0001 — 왜 공통 기반을 먼저 뽑았는가

> 상태: **초안 — 검토 필요**
> 날짜: 2026-07-27 · 결정자: 박정현
>
> ⚠️ 판단 칸은 세션 중 오간 논의를 초안으로 정리한 것이다. **본인 문장으로 다시 쓸 것.**
> ADR의 가치는 "무엇을 했나"가 아니라 "왜 그렇게 판단했나"에 있고, 그 이유는
> 3개월 뒤 다른 사람에게 설명할 사람이 직접 갖고 있어야 한다.
> 동의하지 않는 문단은 지우고 다시 쓰는 편이 낫다 — 반박이 가장 빠른 검증이다.

## 맥락 — 결정 시점의 사실

### 덱의 순서와 우리 순서가 다르다

원 덱(테크세미나 2026-07-24)의 9단계는 `제어 → 실행 → 관측 → 제품 → 조율 → 복제` 순서였고,
공통 기반 상속은 **9번(마지막)** 이었다. 우리는 그것을 **1번**으로 당겼다.

### 측정된 상태 (2026-07-27)

| 항목 | 통합 전 | 비고 |
|---|---|---|
| venv | **5벌 · 680MB** | Python 3.9.6 1벌 + 3.14.6 4벌 (버전 혼재) |
| `requirements.txt` | 6개 | 버전 범위 충돌 2건 |
| `.env` | 6개 | `NOTION_TOKEN` 3벌 · `APIFY_TOKEN` 2벌 |
| Gmail 자격증명 | `token.json` 4벌 | **refresh_token·client_id 전부 동일** — 물리적 복사본 |
| 노션 클라이언트 | 별개 구현 2개 | net-sourcing 1,345줄 vs bplan 인라인 |
| Slack 발송 | 2방식 | webhook · bot 토큰 |
| 절대경로 | 11곳 | + 교차 스킬 참조 3곳 |
| 실데이터 | **314MB가 리포 안** | `git clean -xdf` 사정권 |

### 대안

| 안 | 내용 |
|---|---|
| A | 공통 기반을 먼저 추출한다 (채택) |
| B | 덱 순서대로 제어(승인 브릿지)부터 만든다 |
| C | 공통화하지 않고 스킬별로 각자 발전시킨다 |

## 결정

**공통 런타임(kv-core)을 12주의 1번으로 둔다.**

### 왜 A인가

**이 단계는 기능을 만드는 단계가 아니라, 앞으로 만들 것의 단가를 정하는 단계이기 때문이다.**

12주 로드맵에 남은 것은 게이트(W2) · 잡 러너(W3) · 재개(W4) · 검증(W5) · 관측(W7) ·
승인(W8)이다. 이 여섯은 전부 **모든 스킬이 공통으로 필요로 하는 것**이다.
공통 계층 없이 만들면 각각을 스킬 수만큼 만들게 된다.

```
공통 계층 없이 W2~W8:   6개 기능 × 5개 스킬 = 30번 구현
공통 계층 먼저:         6개 기능 × 1번    +  스킬별 배선
```

즉 A를 고른 이유는 "정리가 잘 돼서"가 아니라 **뒤에 올 작업량을 5분의 1로 줄이기 위해서다.**
그리고 이 이득은 **한 번 놓치면 회수할 수 없다** — W2에서 게이트를 5벌 만들고 나면,
나중에 공통화해도 이미 만든 5벌을 걷어내는 비용이 추가로 든다.

**두 번째 이유는 이식 가능성이다.** 시크릿 저장 방식 · 경로 기준 · 공통과 고유의 경계
셋은 이 단계에서 정해지고, 셋 다 **나중에 바꾸기가 매우 비싸다.**
Keychain을 썼으면 머신 이전이 불가능했고, 절대경로가 하나라도 남았으면
`clone → 설정 → 실행` 이 성립하지 않는다. W12에서 발견하는 것보다 지금 정하는 편이 싸다.

**세 번째는 이미 발생한 부채다.** 덱에서 상속이 9번인 것은 발표자가 제품을 만들면서
자연스럽게 공통 부품을 얻었기 때문이다. 우리는 반대다 — 제품 6개를 먼저 만들어
**복제가 이미 부채로 쌓여 있는 상태**에서 시작했다. 덱은 기반이 결과였고, 우리는 전제다.

### 왜 B가 아닌가 — 덱 순서(제어부터)를 따르지 않은 이유

**덱의 순서는 보편 법칙이 아니라 그 사람의 병목이 나타난 순서다.**

덱에서 승인 브릿지가 2번인 이유는 1번(상시 머신에 에이전트 상주)이 있었기 때문이다.
에이전트가 서버에 살고 사람이 옆에 없으니 원격 승인이 필요해진 것이다.

**우리는 1번이 보류다.** 상시 가용 머신이 없다. 그러면 "사람이 옆에 없는 상태"가 아직
발생하지 않았고, 2번의 전제 자체가 성립하지 않는다. 전제 없는 단계를 먼저 만들면
**쓰이지 않는 기능을 만들게 된다.**

같은 이유로 덱의 8번(usage-gate)을 2번으로 당겼다. 덱에서 8번인 이유는 제품이 생긴
뒤에야 쿼터 경쟁이 발생했기 때문인데, **우리는 그 사고가 이미 났다**(무승인 6런 $5.94,
계정 정지). 이미 터진 문제가 아직 안 터진 문제보다 앞이다.

> 배울 것은 순서 자체가 아니라 **"무엇이 무엇의 전제인가"를 따지는 습관**이다.
> 덱을 그대로 베끼는 것은 남의 병목을 내 순서로 삼는 것이다.

### 왜 C가 아닌가 — 공통화하지 않는 선택지

C(스킬별로 각자 발전)는 **단기적으로 가장 싸고, 12주 목표와 정면으로 충돌한다.**

W11의 완료 판정이 *"새 기능에서 새로 쓴 코드가 도메인 로직뿐"* 이다. 이것은
공통 기반이 있어야만 성립하는 문장이다. C를 고르면 W11을 판정할 방법 자체가 없어진다.

그리고 C는 **이미 실패하고 있었다.** 공통화를 안 했더니 자연 발생한 것들:

| 증상 | 실측 |
|---|---|
| 같은 값이 여러 벌 | `NOTION_TOKEN` 3벌 · `APIFY_TOKEN` 2벌 |
| 같은 자격증명의 물리 복사본 | `token.json` 4벌 (refresh_token 전부 동일) |
| 같은 일을 하는 별개 구현 | 노션 클라이언트 2개 · Slack 발송 2방식 |
| 몰래 생긴 결합 | 스킬이 다른 스킬의 파일을 직접 읽는 곳 3군데 |

특히 마지막 항목이 결정적이다. **격리하려고 안 합친 것이 오히려 통제되지 않는 결합을
만들었다.** 명시적 공통 계층이 없으면 필요는 사라지지 않고 **음지에서 절대경로로 연결된다.**

## 결과 — 실제로 무엇이 바뀌었나

### 구조

```
~/kv-automation/   코드    git 관리 · 972MB → 195MB
~/kv-data/         데이터   315MB · rsync 단위 · git 명령이 닿지 않는다
~/kv-config/       시크릿   .env 1개 + 자격증명 3개 · 권한 600
```

### 측정

| 항목 | 전 | 후 |
|---|---|---|
| venv | 5벌 680MB | **1벌 184MB** |
| `.env` | 6개 | **1개** |
| Gmail 자격증명 | 4벌 | **1벌** (재인증도 1회) |
| 파이썬 버전 | 3.9.6 + 3.14.6 | **3.14.6 단일** |
| 절대경로 | 11곳 | **0곳** |
| 교차 스킬 참조 | 3곳 | **0곳** |
| 활성 스킬 | 7종 | **5종** (2종 아카이브) |

### 검증

- `mail-harness/core/selfcheck.py` 실측 통과 — 통합 자격증명으로 Gmail 라이브 연결
- 전 스킬 모듈 import 통과 · 통합 venv에서 동작
- `git clean -xdf` 가 심볼릭 링크만 지우고 대상은 남기는 것을 **실측으로 확인**

### 대가 — 무엇을 잃었나

**① 변경의 폭발 반경이 커졌다.**
전에는 한 스킬을 고치면 그 스킬만 깨졌다. 이제 `kv_core` 를 고치면 **3개 스킬이 동시에**
영향을 받는다(현재 kv_core 사용: mail-harness · net-sourcing · ai-consumer-pulse).

이 위험은 이론이 아니라 **W1 안에서 실제로 터졌다.** venv를 1벌로 합치면서
investment-memo 의 의존성을 빠뜨렸고, 그 스킬이 통째로 안 돌았다. 검증 단계에서 잡았지만
커밋 `fc4d50e` 시점에는 깨진 상태였다.

→ 완화책으로 리포 루트 `requirements.txt` 를 설치의 정본으로 두었다. 다만 **근본 대응은
W5(산출물 검증)와 W9(장애 주입)** 이고, 그때까지는 사람이 눈으로 확인하는 구간이 남는다.

**② 스킬 단위 롤백이 어려워졌다.**
전에는 스킬 폴더만 되돌리면 그만이었다. 이제 스킬의 동작이 kv-core 버전에 의존한다.
공통 계층을 되돌리면 그 위의 전부가 함께 되돌아간다.

**③ 간접층이 생겨 읽기가 조금 어려워졌다.**
`PROJ / "data"` 는 한눈에 보이지만 `paths.data("mail-harness", "harness")` 는
`$KV_DATA` 가 무엇인지 알아야 읽힌다. 이식 가능성을 얻는 대신 **직관성을 조금 지불했다.**

**④ 새 스킬의 진입 비용이 생겼다.**
이제 스킬을 만들려면 kv-core 규약(경로·시크릿·알림 접근 방식)을 먼저 알아야 한다.
이건 W11에서 회수될 것으로 기대하지만, **회수되기 전까지는 순수 비용이다.**

**⑤ 12주 중 1주를 썼는데 운영 성숙도는 0 이동했다.**
성숙도 7축(상태 기록·검증·재개·비용 가드·관측·무인 실행) 중 움직인 것이 없다.
자가점검 8문항도 3/8 → 4/8 로, 움직인 건 재사용 항목 하나뿐이다.
**설계대로이지만, 기반은 늦게 티가 난다는 사실을 기록해 둔다.** 일정이 밀릴 때
W11을 먼저 버리라는 규칙이 여기서 나온다.

## 이 결정이 틀렸다면 어떻게 알 수 있나

선언이 아니라 **관측 가능한 신호**로 적는다. 하나라도 보이면 경계를 다시 본다.

### 🔴 결정적 신호 — 보이는 즉시 멈춘다

**`kv_core` 안에 스킬 이름 분기가 생긴다.**
```python
if skill == "net-sourcing":   # ← 이게 보이면 경계를 잘못 그은 것이다
```
공통 계층이 특정 스킬을 알아야 한다면 그건 공통이 아니다. 도메인이 위로 새어 올라온 것이다.

**스킬이 `kv_core` 를 우회하기 시작한다.**
`paths.data()` 대신 직접 경로를 쓰거나, `secrets.get()` 대신 파일을 직접 읽는 코드가 생기면
공통 계층이 실제 필요를 못 담고 있다는 뜻이다. **우회는 항상 불편함의 증거다.**

### ⚠️ 경고 신호

| 신호 | 무엇을 뜻하나 | 측정 방법 |
|---|---|---|
| N번째 이식이 첫 번째보다 느리다 | 경계가 잘못됐거나 추상화가 과하다 | 이식당 추가 줄 수 (현재 56 → 16 → 10) |
| `kv_core` 를 고칠 때마다 전 스킬 테스트가 필요하다 | 결합이 과하다 | 커밋당 영향 스킬 수 |
| 새 스킬을 추가하려면 `kv_core` 를 먼저 고쳐야 한다 | 공통 계층이 확장에 안 열려 있다 | 신규 스킬 추가 시 kv-core 변경 여부 |
| W11에서 도메인 외 코드를 새로 쓰게 된다 | 상속이 실제로는 안 되고 있다 | "새로 쓴 것 vs 상속한 것" 표 |
| 같은 버그를 스킬마다 따로 고치고 있다 | 공통화가 덜 됐다 | 유사 수정의 반복 횟수 |

### 판정 시점

**W11이 최종 판정이다.** 비플랜 스코어링 · 후속 액션 · IVC 4단계를 만들 때
**새로 쓴 코드가 도메인 로직뿐이면 이 결정이 옳았고**, 잡·게이트·검증·관측·알림을
또 쓰게 되면 틀렸거나 부족했던 것이다.

그 전 중간 점검은 **W2**다. `gate.py` 본체를 kv-core에 한 번 만들어서 5개 스킬에
배선하는 것이 자연스러운지, 아니면 스킬마다 예외가 필요한지가 첫 시험이다.
